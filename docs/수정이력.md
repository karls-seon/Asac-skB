## 38. SKT 온라인 전용(다이렉트)이 통째로 빠져 있었다 — 그리고 딸려 나온 두 가지

### 발단

`0 청년 다이렉트 48`의 SKT 페이지에는 *"만 34세 이하 고객님이 T 다이렉트샵에서
신규가입, 기기변경 또는 유심을 개통한 경우에만 가입하실 수 있습니다"*가 있는데
우리 데이터의 `age_condition`은 비어 있었다.

### 원인 — 파싱이 아니라 수집 범위

SKT 크롤러는 `만 34세 이하`를 **이미 잘 잡고 있었다**(99행 중 41행). 문제는
`COLLECTED_CATEGORIES = {"베스트", "라이트"}`라 `다이렉트` 카테고리 31개가
통째로 수집 대상이 아니었던 것이다.

```
SKT 카테고리 118개 중
  ('다이렉트', '일반')          15   ← 0 청년 다이렉트 30/34/42/48/55/62/69
  ('다이렉트', '넷플릭스 혜택')     5
  ('다이렉트', '티빙&웨이브 혜택')   3
  ('다이렉트', '디즈니+ 혜택')      3
  ('다이렉트', 'T우주 혜택')       3
  ('다이렉트', '유튜브 프리미엄')    1
  ('다이렉트', '스마트기기 혜택')    1
```

KT는 `온라인전용(요고)`, LGU+는 `너겟`을 수집하는데 **SKT만 온라인 전용이
빠져 있어 3사 비교가 비대칭**이었다. 모요를 통해 일부가 들어오긴 했지만
모요 상세에는 가입 연령이 아예 없다(원본 캐시로 확인 — "이미 SKT 요금제를
쓰고 있다면 가입할 수 없어요"만 있음).

### 딸려 나온 문제 1 — 0원 요금제 31개

`다이렉트`를 수집 범위에 넣자 `discounted_fee`가 **전부 0원**이 됐다. SKT API가
할인 대상이 아닌 요금제에 `selAgrmtAplyMfixAmt = "0"`을 준다. "공짜"가 아니라
"해당 없음"이다. 0은 결측과 달리 예산 필터를 통과하고 **정렬 맨 위**로 온다.

KT 요고에서 이미 한 번 겪은 유형이다(`5644652`, 온라인전용은 선택약정 대상 아님).
`_selective_discount()`로 분리해 정가보다 작을 때만 할인가로 쓴다.

### 딸려 나온 문제 2 — 3사 최저가 라인 90개가 추천에서 사라져 있었다

할인이 없으면 `discounted_fee`가 비는데, 명세서는 *"두 통신사 유형을 함께
비교할 때는 `discounted_fee` 기준으로 보라"*고 한다. **할인 없는 요금제가
비교에서 사라지는 구조**였다.

| 통신사 | 빠져 있던 요금제 |
|---|---|
| KT 요고 | 13 |
| LGU+ 너겟 | 46 |
| SKT 다이렉트 | 31 |
| **합** | **90 (MNO 593개의 15%)** |

`merge_plans.fill_undiscounted_fee()`로 정가를 채운다. 할인 여부는
`discount_type`(빈값)과 `monthly_fee == discounted_fee`로 여전히 구분된다.

**효과**: 통신3사·예산 5만원·50GB 조건의 후보가 **3개 → 22개**가 됐고,
넷플릭스 최저가가 66,750원 → **59,000원**(너겟59)으로 내려갔다.

### 모요발 행에 조건을 빌려주기

모요는 3사 자사상품을 함께 싣지만 가입 연령을 적지 않는다. 같은 **통신사·같은
이름**의 3사 직접 수집분에 조건이 있으면 가져온다(`borrow_age_condition()`).
10행이 채워졌고, 전부 SKT `0 청년` 계열이다. 이름이 같아도 통신사가 다르면 다른
상품이라 `host_mno`까지 맞을 때만 쓴다.

### 확인 방법

```bash
python src/crawl_skt.py --parse-only   # 다이렉트 31행, 0원 0건
python src/merge_plans.py              # "모요발 10행", "할인 없는 요금제 90행" 출력
```

```python
recommend(plans, budget=60_000, data_gb=100, mvno_ok=False, age=40)  # 0 청년 0개
recommend(plans, budget=60_000, data_gb=100, mvno_ok=False, age=27)  # 0 청년 4개
```

## 37. 컬럼을 액면 그대로 읽으면 틀리는 네 가지

앞의 항목들과 성격이 다르다. **크롤링은 맞게 했는데 읽는 쪽이 틀렸다.** 추천
로직(`src/recommend.py`)을 만들며 드러난 것이라, 이 CSV를 쓰는 사람이면 누구나
같은 함정을 밟는다.

### 37-1. `data_throttle_speed`가 두 가지를 가리킨다

`data_unlimited == True`인 351개 중 186개에 속도 제어가 붙어 있다. 이걸 전부
"소진 후 느려지는 요금제"로 보면 **8~9만원대 통신3사 프리미엄 180개가 억울하게
탈락한다.**

| 실제 의미 | 개수 | 예시 | 구분 신호 |
|---|---|---|---|
| **테더링** 한도 초과 시 속도 | 180 | KT `초이스 더블` — 테더링 90GB 후 100Kbps. 본 데이터는 무제한 | `tethering_gb`가 **채워져 있음** |
| **본 데이터** 소진 후 속도 | 6 | 모요 `시월 무제한 7GB+1Mbps` | `tethering_gb`가 **빔** |

180 대 6으로 정확히 갈리고 겹침이 0이다. `recommend.full_speed_unlimited()`가
이 규칙을 쓴다.

### 37-2. `daily_data_gb`만 있고 `data_gb`가 빈 요금제 61개

`data_gb`로만 거르면 무제한도 아니어서 통째로 탈락한다. `일 5GB × 30 = 월 150GB`로
환산해야 후보에 들어온다. 예산 2만원·50GB 조건에서 **19개가 새로 나타난다.**
`recommend.usable_gb()` 참고.

### 37-3. 같은 요금제가 연령·옵션 변형으로 여러 행

`base_plan_id`가 같은 행이 441개다. 두 종류가 섞여 있다.

```
1693_베이직30GB              (조건 없음)      ← 나이를 안 받으면 5행이 전부 통과
1693_베이직30GB_만 34세 이하
1693_베이직30GB_만 18세 이하
1693_베이직30GB_만 65세 이상
1693_베이직30GB_만 75세 이상

1681_초이스130 (넷플릭스)     selected_option  ← 이쪽은 사용자가 하나를 고르는 것
1681_초이스130 (디즈니+)
1681_초이스130 (유튜브 프리미엄)
```

목록을 보여줄 때는 `base_plan_id`로 하나만 남겨야 한다. 단 **어느 것을 남기느냐가
중요하다** — 사용자가 넷플릭스를 원하면 넷플릭스 옵션이 살아남아야 하므로,
정렬을 마친 뒤에 중복을 제거한다.

### 37-4. `ott_options`는 등급이 지워진 요약값이다

`schema.summarize_benefits()`가 `normalize_service()`로 서비스명만 남긴다.

```
혜택 테이블  '티빙'                        17,000원 명시 (3행)
             '티빙 광고형 스탠다드 (12개월)'  금액 없음   (19행)
             '티빙&웨이브 광고형 50% 할인'    할인이지 제공이 아님
                     ↓ 요약
ott_options  '티빙'   ← 셋 다 같은 값이 된다
```

혜택의 **가치**를 매기려면 요약 컬럼이 아니라 `plan_id`로 혜택 테이블을 조인해
`benefit_name`을 봐야 한다. 티빙이 붙은 요금제 35개 중 사이트가 금액을 명시한 건
3개뿐이다.

### 확인 방법

```bash
python src/recommend.py     # 위 네 가지를 assert로 검사한다
```

## 36. 모요 혜택 2,322건이 전부 "사은품/페이백" 하나였다

### 증상

`통신요금제_혜택상세_최종.csv`에서 `carrier_type == "MVNO"`인 혜택 2,322건의
`benefit_category`가 **전부 `사은품/페이백`** 이고 나머지 5개 카테고리가 0건이었다.
3사(MNO)는 6개 카테고리가 정상적으로 갈렸다.

혜택 이름을 열어 보면 실제로는 섞여 있었다.

- `밀리의 서재 평생 구독 0원`, `티빙 광고형 스탠다드 제공 (12개월)` — OTT/구독
- `SOLO결합 데이터 10GB 지급`, `솔로결합(+20GB)`, `추가데이터 10GB 제공` — 추가데이터
- `U+ 멤버십 VIP콕` — 멤버십
- `일반유심/배송비 무료`, `네이버페이 5,000원` — 이건 진짜 사은품이 맞다

**파급**: 요금제 테이블의 `ott_options` / `ott_option_count`는 혜택 테이블에서
파생되므로 MVNO 2,229행의 `ott_options`가 전부 빈값이었다. 추천에서 "OTT 원함"을
조건으로 걸면 알뜰폰이 전량 부당하게 탈락한다.

### 원인 — 링크 종류로 카테고리를 정하고 있었다

`crawl_moyo.parse_detail()`이 상세페이지의 `<a href="/gift-group/...">`를 훑으면서
카테고리를 문자열 리터럴 `"사은품/페이백"`으로 **박아 넣고** 있었다. 모요는 OTT
구독권도, 결합 추가데이터도, 멤버십도 전부 같은 `/gift-group/` 링크로 붙여 놔서
링크 종류는 카테고리의 근거가 못 된다. 3사가 쓰는 공용 `classify_benefit_name()`을
모요만 안 쓰고 있었다.

### 수정

1. 모요도 3사와 같은 `classify_benefit_name(label, "사은품/페이백")`을 쓴다.
   이름에 단서가 없을 때만 사은품으로 떨어진다.
2. `classify_benefit_name()`에 **추가데이터 규칙이 아예 없었다**(SKT 크롤러 안에만
   지역 규칙으로 있었다). `EXTRA_DATA_RE`로 공용 함수에 넣었다. `데이터`라는 말이
   없는 `솔로결합(+20GB)` 표기까지 잡으려고 `(데이터|결합) … (추가|공유|쉐어|결합|N GB)`
   형태로 본다.
3. **OTT/구독·추가데이터 판정을 사은품보다 먼저** 하도록 순서를 바꿨다.
   `구글 AI프로+도미노피자 할인쿠폰`(42건), `데이터쿠폰 20GB`(23건)처럼 구독·데이터
   혜택에 '쿠폰'이 딸려 오는 이름이 쿠폰 쪽으로 먼저 걸려서 통째로 사은품이 되고 있었다.
   최종 순서: OTT/구독 → 보험 → 스마트기기 → 멤버십 → 추가데이터 → 사은품 → default.

### 전수 검증 (1~2건 표본으로 일반화하지 않았다 — 34번의 교훈)

규칙을 바꾸기 전에 4개 사이트 혜택 5,072행 전체에 후보 규칙을 적용해 before/after를
뽑고, **바뀌는 이름 62종을 전부 눈으로 확인**했다.

- 순서 변경의 영향 범위: 3사 **0행**, 모요 67행(3종). 쿠폰류 키워드가 OTT 키워드나
  추가데이터 패턴과 동시에 걸리는 혜택명이 3사엔 하나도 없다(각각 0건).
- 추가데이터 규칙이 잡은 340행 = 34종을 전수 확인 — 오탐 0.
- 수정 후 `--parse-only` 재파싱 결과를 이전 interim과 행 단위로 대조:
  **kt/skt/lguplus는 카테고리 변경 0행**(회귀 없음), 모요만 642행 변경.

| carrier_type | before | after |
|---|---|---|
| MVNO 사은품/페이백 | 2,322 | 1,710 |
| MVNO OTT/구독 | 0 | 272 |
| MVNO 추가데이터 | 0 | 340 |
| MVNO `ott_options` 채워진 요금제 | 0 / 2,229 | 244 / 2,229 |

모요가 파는 온라인 전용 요금제 45개는 `carrier_type=MNO`라, 모요발 혜택 30행이
MNO 쪽 집계에 들어간다(MNO 사은품 190 -> 160, OTT 728 -> 754, 멤버십 294 -> 297,
스마트기기 348 -> 349). 3사 크롤러 출력이 바뀐 게 아니다.

### 확인 방법

```bash
python src/schema.py          # 분류 규칙 자체 점검 14건 (실제로 걸렸던 이름들)
```

MVNO 카테고리가 다시 한 종류로 뭉치면 회귀다.

### 남은 한계

- `토스미·오픽미 AI 모의고사`(27건)가 `AI` 키워드 때문에 OTT/구독으로 잡힌다.

## 35. KT가 요금표를 외부 JS로 옮겨서 주력 4개 상품이 통째로 사라졌다

### 증상

2026-08-03 갱신에서 KT가 **259행 -> 29행(-89%)**이 됐다. 갱신 리포트는
"신규 8 / 변경 82 / **단종 235**"를 보고했는데, KT가 하루 만에 요금제를 90%
없앴을 리는 없다.

사라진 것은 **초이스 / 초이스더블 / 베이직 / 베이직(이월)** 4개 상품군이고,
음성 / 요고 / 키즈 / 웰컴은 멀쩡했다.

### 원인 — tableHTML이 페이지 안에서 외부 JS 파일로 빠졌다

KT 상세 페이지는 연령별 요금표를 `tableHTML`이라는 JS 변수에 통째로 담아
페이지 안에 넣어 뒀고, `extract_tablehtml_by_age()`가 그걸 정규식으로 꺼내
쓴다. 그런데 위 4개 상품이 새 템플릿으로 바뀌면서 이 데이터가 **별도 JS
파일로 분리**됐다.

```html
<script src="/static/prodetail/1693/web/js/data/w_basic_data.js"></script>
```

`fetch_combined_html()`은 상세 페이지 + `forte`/`accordion`/`htmlUploadType`
조각까지만 받아 붙이고 있어서, 이 JS 파일은 받지 않았다. 그 결과 4개 상품의
요금표가 **통째로 빈 채로** 파싱돼 0건이 됐다. 파일명은 상품마다 다르다
(`w_choice_data` / `w_choice_double_data` / `w_basic_data` /
`w_basic_carry_over_data`).

### 수정

`fetch_combined_html()`이 조각까지 다 붙인 **뒤에** `js/data/*.js` 경로 패턴을
찾아 그 파일도 이어 붙인다. 파일명을 하드코딩하지 않아 KT가 새 상품에 같은
구조를 쓰더라도 자동으로 따라간다. `<script>` 태그가 본문이 아니라
`htmlUploadType` 조각 안에 있는 경우가 있어서, 반드시 **조각을 붙인 뒤**
찾아야 한다.

```python
for src in dict.fromkeys(re.findall(r'<script[^>]+src="([^"]*?/js/data/[^"]+\.js)"', combined_html)):
    combined_html += "\n" + _get(f"https://product.kt.com{src}")
```

기존 `tableHTML` 파싱 로직은 **한 줄도 안 고쳤다.** 데이터가 있는 위치만
바뀌었을 뿐 형식은 같아서, 받아오기만 하면 그대로 파싱된다.

### 곁들여 발견한 실제 상품 변화

되살리고 보니 KT가 **초이스 더블을 개편**해 놓았다(ItemCode도 1691 -> 1692로 바뀜).

| | 이전 | 현재 |

| 초이스 더블 구성 | 디즈니플러스+폰케어 1종 | **4종** (유튜브+넷플릭스 / 유튜브+디바이스 / 디바이스 / 디즈니플러스+폰케어) |

페이지 HTML 주석에 `<!-- 8월 11일 반영 ... 유튜브 프리미엄+구글 AI Plus -->`가

### 가드를 뚫고 지나갔다 — 전체 비율만 보고 있었다

## 34. 모요 페이백 가치 저평가·이중계산 수정 + 가격 쪽은 손댔다가 되돌림

### 증상

`https://www.moyoplan.com/plans/23450`(통화 충분 15GB)을 보다가 이상한 점을
발견했다. 사이트에는 "월 납부액 16,900원 / 페이백 포함하면 월 0원"이라고
나오는데, 우리 CSV는 `monthly_fee=16900, discounted_fee=0`으로 저장하고
있었다. 실제로 매달 16,900원이 청구되고 네이버페이로 20,000원을 별도로
돌려받는 것뿐인데, `discounted_fee=0`은 마치 요금 자체가 0원인 것처럼 보인다.

같은 페이백이 혜택 테이블에도 `benefit_value_won=20,000`으로 잡혀 있었는데,
실제 페이백 총액은 "매달 2만원 씩 6개월"이므로 120,000원이어야 했다(6분의 1로
저평가). 다른 플랜(10390)에서는 같은 페이백이 **두 번** 잡혀 있었다 —
저평가된 값(5,000원)과 올바른 값(30,000원)이 별개 행으로 둘 다 존재했다.

### 원인 — 페이백 텍스트를 두 곳에서 각자 다르게 처리하고 있었다

`crawl_moyo.py`가 페이백을 처리하는 경로가 3곳이었는데, 서로 어긋나 있었다.

1. **목록 카드 가격**: "페이백 포함 월 X원 N개월 이후 Y원"에서 `discounted_fee`로
   X(=`fees[0]`)를 그대로 썼다. X는 moyo가 페이백을 미리 넣어 계산한 마케팅용
   체감가라 실제 청구액과 다르다.
2. **사은품 링크 파싱**(`<a href="/gift-group/...">`): "네이버페이 매달 2만원
   페이백 (6개월)"류 라벨을 `_parse_krw()`로 그대로 넘겼다. 이 함수는 라벨
   안의 숫자 중 **가장 큰 값 하나**만 쓰도록 설계됐는데(`"19.2만원(매월
   3.2만원씩)"`처럼 총액이 이미 적힌 사은품엔 맞는 로직), 이 라벨은 총액이 아니라
   **1회분 금액만** 적혀 있어서 그 1회분(2만원)이 그대로 전체 가치로 기록됐다.
3. **전용 정규식**(`"매달 N원 씩 M개월"`로 총액을 계산하도록 만든 코드): 금액
   단위로 `원`/`천원`만 인식하고 **`만원`을 인식하지 못했다.** "2만원"에 대해서는
   매칭이 애초에 실패해 조용히 건너뛰었고, "5천원"처럼 천원 단위인 경우에만
   성공해서 **2번 경로와 별개로 또 하나의 행**을 만들었다(플랜 10390이 이 경우).

즉 "만원" 단위면 2번 경로만 살아남아 저평가되고, "천원" 단위면 2번(저평가)과
3번(정확)이 **둘 다** 남아 이중 계산됐다. 전수 확인 결과 사은품 라벨 중
"매달" 반복 페이백 표현이 121건 있었는데, 그중 42건만 전용 정규식과도 겹쳤다
(나머지 79건은 만원 단위거나 "평생"처럼 개월 수가 없어 전용 정규식이 애초에
안 걸렸다).

### 수정 (혜택 가치 — 반영됨)

전용 정규식 블록을 통째로 제거하고, 사은품 링크 파싱 쪽에
`_recurring_payback_won()`을 추가했다. "매달 N원 페이백 (M개월)" 구조를
알아보면 `_parse_krw`로 1회분 금액을 정확히 읽은 뒤(만원·천원·원 모두 지원)
개월 수를 곱해 총액을 만든다. "평생"처럼 개월 수가 없으면 총액을 낼 수
없으므로 1회분 금액만 남긴다(과대평가보다 낫다). 경로가 하나로 합쳐졌으니
이중 계산도 함께 사라진다.

```python
_RECURRING_PAYBACK_RE = re.compile(
    r"매달\s*([\d,.]+\s*(?:만|천)?\s*원)\s*(?:씩)?\s*페이백.*?(\d+)\s*개월")
```

### 가격 쪽은 고쳤다가 되돌렸다 — Y도 "지금 가격"이 아닐 수 있다

처음엔 "카드의 X(체감가)가 아니라 Y(`regular_fee`, N개월 이후 가격)를
`discounted_fee`로 쓰면 된다"고 생각해 그렇게 고쳤었다. 그런데 다른 페이백
플랜들을 더 찾아보니(`23450`·`10390` 두 건만으로 판단한 게 성급했다) **Y도
지금 청구액이 아닌 경우**가 있었다.

```
plan 30954: 카드 표기 "페이백 포함 월 12,800원 / 7개월 이후 43,400원"
            상세페이지 "월 납부액": 17,800원   ← X도 Y도 아님!
```

Y(43,400원)는 "체감가 혜택이 끝난 뒤 **나중에** 적용될 가격"이지 지금
청구되는 금액이 아니었다. 실제로 지금 매달 나가는 돈(17,800원)은 상세페이지
"월 납부액" 줄에만 있고, 목록 카드 텍스트만으로는 계산해낼 수 없다. `Y`로
바꾸면 이 플랜이 가진 **진짜 임시 할인**(17,800원이 정가보다 낮다는 사실)이
통째로 사라지는 새로운 오류가 생긴다 — 원래 문제(체감가 X를 쓰던 것)와
성격은 다르지만 마찬가지로 부정확하다.

**되돌렸다.** `discounted_fee`는 다시 카드의 X(체감가)를 쓴다. X가 정확한
청구액이 아닌 경우가 있다는 걸 알지만, 상세페이지 "월 납부액"을 새 필드로
긁어오기 전까지는 이게 그나마 덜 틀린 값이라고 판단했다. `discount_type`/
`discount_period_months`는 그대로 둬서 "이 요금제엔 페이백이 있다"는 정보는
남긴다.

**다음에 제대로 고치려면**: 상세페이지 "월 납부액" 줄을 새 필드로 파싱해서
`discounted_fee`의 진짜 출처로 삼아야 한다. 그러면 X(체감가, 참고용으로 남길
수도 있음)·Y(미래가)·실제 청구액 셋을 컬럼으로 분리해 관리할 수 있다.

### 알려진 한계 (아직 안 고침)

"매달 N원 (M개월)" 반복 지급 표현이 "페이백"이라는 단어 없이 나오는 경우가
있는데(`_RECURRING_PAYBACK_RE`가 "페이백" 리터럴을 요구해서) 이런 건 여전히
저평가된다.

```
plan 37112: "매달 Npay 5천원 (7만)"        -> 5,000으로 기록 (7만원=70,000이 맞아 보임)
plan 26273: "매달 hy 금액권 1만원(12만)"    -> 10,000으로 기록 (12만원=120,000이 맞아 보임)
```

두 사례 다 괄호 안 숫자에 "원"이 빠져 있어(`12만`, `7만`) `_parse_krw`도 총액을
못 읽는다. "페이백"이 아니라 "Npay"/브랜드명 상품권 등 표현이 다양해서, 개별
브랜드 키워드를 나열하기보다 "매달 … (…)" 구조 전체를 더 일반적으로 인식하는
규칙이 필요해 보인다 - 아직 설계 전이다.

## 33. 모요 수집 34분 중 31분이 "타임아웃이 안 걸리는 요청" 탓이었다

### 증상

2026-08-01 갱신이 총 49분 걸렸고 그중 모요 상세 수집이 40분이었다. 상세는
466건만 받았는데도(전체 2,299건 중 신규·변경분만 골라서) 건당 평균 4.42초였다.

### 평균이 원인을 가리고 있었다

건당 간격 분포를 보니 **중앙값은 0.40초**로 정상이었고, 소수의 극단값이
시간을 다 먹고 있었다.

| 간격 | 건수 | 전체 시간 중 |
|---|---|---|
| 0~0.5초 | 291 | 5.1% (1.8분) |
| 0.5~3초 | 68 | 5.4% (1.9분) |
| 3~10초 | 61 | 18.6% (6.4분) |
| 10~30초 | 32 | 27.1% (9.3분) |
| **30초 이상** | **13** | **43.8% (15.0분)** |

최장 **269초**(4.5분). 상위 106건(23%)이 전체의 89%를 차지했다.

### 원인 — urlopen의 timeout은 총 시간 제한이 아니다

`_get`은 `urlopen(req, timeout=20)`으로 20초 제한을 걸었다고 생각했는데,
이 값은 **소켓 작업 하나당** 제한이다. 서버가 데이터를 조금씩 끊이지 않게
흘려보내면 각 수신은 20초를 넘지 않으므로 **타임아웃이 영영 안 걸린다.**
269초짜리가 그 경우다 — 사실상 무제한으로 기다리고 있었다.

먼저 의심했던 두 가지는 실측으로 배제했다.

| 가설 | 실측 | 판정 |
|---|---|---|
| 매 요청 새 연결(핸드셰이크) 비용 | 건당 0.09초, 연결 재사용 시 0.05초 | 무관 (절감 0.3분) |
| 캐시 445MB를 매번 다시 읽음 | 2,299개 전부 6초 | 무관 |

정체는 실행 초반부터 끝까지 고르게 흩어져 있었고 마지막 1분이 오히려 가장
빨랐다(34건, 느린 건 0). **서버가 우리를 제한하는 게 아니라 산발적 지연**이므로,
끊고 다시 요청하면 대개 바로 성공한다.

### 수정 — 총 소요 시간을 직접 재서 자르고 재시도

```python
REQUEST_DEADLINE_SEC = 6.0   # 한 번 시도의 총 제한 (중앙값 0.4초의 15배)
REQUEST_ATTEMPTS = 3
SOCKET_TIMEOUT_SEC = 3.0     # 소켓 작업 하나당 제한
```

받는 도중에도 덩어리마다 경과 시간을 확인한다. 소켓 제한을 deadline보다
짧게 둬야 초과분이 작아진다(경과 확인은 덩어리 사이에서만 가능하므로).

> **`read(n)`이 아니라 `read1(n)`이어야 한다.** 처음엔 `read(65536)`로 짰는데,
> 이건 65,536바이트가 다 모일 때까지 내부에서 계속 기다려서 **경과 시간 확인이
> 실행될 기회조차 없다.** 느린 서버를 흉내낸 테스트가 그대로 멈춰 버려서
> 발견했다 — 고치기 전과 동작이 똑같았다. `read1`은 한 번 받은 만큼 바로 돌려준다.

### 검증

2초마다 조금씩만 응답하는 로컬 서버(이론상 120초)로 269초 사례를 재현했다.

```
수정 전: 타임아웃 안 걸림 (120초+ 그대로 기다림)
수정 후: 18.5초에 포기 (상한 28.5초)
```

파싱 회귀도 확인했다 — `--parse-only` 재실행 결과가 2,204행 그대로이고
`crawled_at` 외 **값 차이 0건**.

**확인 방법**: 갱신 로그에서 상세 수집 구간이 30분을 넘으면 다시 이 분포를
재볼 것(`detail_*.html`의 mtime 간격).

### 증상

2026-08-01 갱신 리포트가 **신규 94건 / 단종 63건**을 보고했는데, 그중 40쌍은
**같은 요금제가 신규와 단종에 동시에 나타났다.** 예를 들어:

```
신규: [KT] 초이스130 (유튜브 프리미엄)  plan_id=1681_초이스130_유튜브프리미엄
단종: [KT] 초이스130 (유튜브 프리미엄)  plan_id=1681_초이스130_유튜브 프리미엄
```

이름·통신사·스펙 전부 동일하고 **plan_id의 공백 유무만** 다르다.

### 원인

`schema.expand_select_variants()`가 택1 옵션명에서 공백을 지워 `plan_id`
접미사를 만드는데, 원래 코드가 이랬다.

```python
new_id = f"{plan['plan_id']}_{re.sub(r'\\s+', '', option_name)}"
```

f-string 안의 `r'\\s+'`는 **raw 문자열 안의 이스케이프된 백슬래시** 두 글자라,
정규식으로는 "백슬래시 + s 한 개 이상"을 찾는 패턴이 된다. 한글 옵션명에는
그런 문자열이 없으므로 `re.sub`가 **아무것도 지우지 못하고 원문을 그대로
반환**했다 — 공백 제거 로직이 이름만 있고 처음부터 동작한 적이 없었다.

> 이 줄은 애초에 Python 3.9(f-string 안에 백슬래시 불가)에서는 `SyntaxError`로
> 아예 import조차 안 됐다. 3.12에서 처음 크롤링을 돌렸을 때는 문법 에러 없이
> 조용히 "공백 안 지워짐" 상태로 통과됐다.

### 수정

정규식 자체를 백슬래시 하나(`r'\s+'`, 진짜 "공백" 패턴)로 고치면서, f-string
안에 정규식을 직접 넣지 않고 변수로 뺐다(가독성 + 향후 같은 실수 방지).

```python
option_slug = re.sub(r"\s+", "", option_name)
new_id = f"{plan['plan_id']}_{option_slug}"
```

### 영향 — 1회성 plan_id 포맷 변경

택1 옵션이 있는 요금제(KT 초이스, SKT 베스트, LGU+ 너겟·플러스플랜)는 전부
`plan_id`가 "공백 있음" → "공백 없음"으로 바뀐다. `diff_plans()`는 `plan_id`
기준으로 신규/단종을 가르므로, **실제로는 아무것도 안 바뀐 요금제 40개가
"단종 후 신규"로 잘못 집계됐다.**

```
2026-08-01 리포트 원본:  신규 94 / 단종 63
포맷 변경 아티팩트 제외:  신규 54 / 단종 23  (진짜 변화)
```

앞으로는 신·구 데이터 모두 같은 포맷을 쓰므로 **이 갱신 1회에만 있는 일**이다.
`base_plan_id`(택1로 안 쪼갠 원본 id)는 이 수정과 무관하게 그대로였으므로,
"실제 요금제 수"(`nunique(base_plan_id)`) 집계에는 영향이 없다.

**확인 방법**: 어떤 갱신 리포트의 신규/단종 목록에서 `host_mno`+`plan_name`이
겹치는 쌍이 있으면 의심 — `plan_id`의 공백만 다른지 대조.

## 28. 연령 전용 요금제를 3사 일관되게 되살림 + base_plan_id 연결 버그

### 앞선 판단을 뒤집었다

25~27번에서 "휴대폰 5G/LTE만" 기준으로 좁히면서 KT 키즈/외국인과 SKT 연령특화를
같이 뺐는데, 이건 태블릿·3G를 뺀 것과 **성격이 다른 결정**이었습니다.

| | 왜 빼는가 |
|---|---|
| 태블릿·워치·3G·선불폰 | 음성/문자가 없거나 종량 과금 — **스펙 구조 자체가 다름** |
| 연령 전용 (키즈·유쓰·시니어) | **스펙 구조는 동일**, 가입 자격만 다름 |

연령 전용은 이상치가 아니라 정상 요금제입니다. 빼면 만 25세 사용자에게 실제로 가장
유리한 유쓰 요금제를 영영 추천할 수 없습니다. 게다가 당시 상태는 **LGU+만 52행이
남아 있어**, 추천 모델이 "청년·시니어용은 LGU+에만 있다"는 없는 사실을 학습할 판이었습니다.

캐시에 이미 다 받아져 있어서 재크롤링 없이 되살렸습니다.

```
KT   : TABS에 "키즈/외국인" 추가            → 8행 (키즈38~13, 웰컴5·3·1)
SKT  : COLLECTED_GROUPS로 그룹 단위 선택     → 15행 (연령특화 8 + 기본/표준 3)
LGU+ : 변경 없음                           → 52행
```

> SKT `전용` 카테고리는 3G 24 · 선불폰 12 · 연령특화 8 · 복지 4 · 외국인 4 ·
> 기본/표준 3이 섞여 있어 **카테고리 단위로는 못 받습니다.** 27번에서 확보한
> 그룹명(`prodGrpNm`)을 써서 `(카테고리, 그룹)` 단위로 골랐습니다.

### KT 키즈 요금제의 연령 조건이 이미지 alt에만 있었다

되살리고 보니 KT 8행의 `age_condition`이 전부 비어 있었습니다. 그대로 두면
**키즈13(13,000원)이 일반 성인에게 추천**될 수 있습니다.

처음엔 "KT가 연령을 안 적는다"고 판단해 탭 이름 그대로 `키즈`만 넣었는데,
**틀린 판단이었습니다.** `BeautifulSoup.get_text()`로 본문만 훑었기 때문에
못 봤을 뿐, 실제로는 세 곳에 적혀 있었습니다.

```html
<img alt="만 12세 이하 어린이용" src=".../w_pduct_fte_1695_top_01.png">
<meta name="Description" content="KT 키즈(만 12세 이하) 요금제 서비스를 …">
<script type="application/ld+json"> "description":"KT 키즈(만 12세 이하) …"
```

→ 페이지 HTML 원문에서 `만 N세 이하|미만`을 찾도록 고쳐 **`만 12세 이하`**를
정확히 채웠습니다. SKT ZEM플랜의 ledger 태그와도 표기가 일치합니다.
웰컴 3종은 alt가 `외국인 고객 맞춤 전용 요금제`이고 나이 제한이 없어 `외국인`입니다.

> **교훈**: 텍스트만 훑는 파싱은 `alt`/`meta`/JSON-LD에 있는 정보를 조용히
> 놓친다. "사이트에 없다"고 결론 내리기 전에 원문 HTML을 봐야 한다.

### age_condition 표기 통일 (16종 → 10종)

정확한 값을 채우고 나니, 같은 대상인데 사이트별 표기가 달라 **나이로 거를 수 없는**
상태가 드러났습니다.

| 원문 | 정규화 |
|---|---|
| `청년(Y덤)` (KT) · `청년(만 34세 이하)` (SKT) · `만 19세 ~ 35세 미만` (LGU+) | `만 34세 이하` |
| `스쿨덤(청소년)` (KT) · `청소년(만 18세 이하)` (SKT) · `만 13세 ~ 19세 미만` (LGU+) | `만 18세 이하` |
| `만 4세 ~ 13세 미만` (LGU+) | `만 12세 이하` |
| `65세 이상` (KT) · `시니어(만 65세 이상)` (SKT) | `만 65세 이상` |

`schema.normalize_age_condition()` 한 곳에서 처리하고, 4개 크롤러가 값을 만들 때
통과시킵니다. 구간 표기는 **상한만** 남깁니다(추천에서 걸리는 건 상한이므로).
연령이 아닌 자격(`외국인`, `복지카드 소지 시`)은 원문 유지.

KT의 `AGE_TIER_LABELS`는 `plan_id` 접미사에도 쓰이므로 상수 자체를 정규화 형태로
바꿨습니다. 안 그러면 `plan_id`는 `_청년(Y덤)`인데 컬럼은 `만 34세 이하`로 어긋납니다.

> 정규식을 `만\s*(\d+)\s*세\s*(이하|미만)`으로 짰다가 LGU+ 구간 표기
> (`만 4세 ~ 13세 미만`)를 통째로 놓쳤습니다. 상한 쪽에는 "만"이 안 붙어서
> `(\d+)\s*세\s*(이하|미만)`으로 완화하고 **마지막 매치**(=상한)를 쓰도록 고쳤습니다.

### base_plan_id 연결 버그 (KT 84행)

같은 점검 중 발견했습니다. KT 덤 행의 `base_plan_id`가 **자기 자신**을 가리키고
있었습니다(`1693_베이직100_청년(Y덤)` → `1693_베이직100_청년(Y덤)`). SKT의
`_age_variant`는 원본을 제대로 넣는데 KT만 빠져 있었습니다.

문서에 `실제 요금제 수 = nunique(base_plan_id)`라고 정의해 뒀으므로, KT만 나이
단계 수만큼 부풀어 있었습니다.

추가로 `expand_select_variants`가 `base_plan_id`를 무조건 덮어써서,
`초이스130_청년(Y덤)_넷플릭스`의 원본이 진짜 원본(`초이스130`)이 아니라
`초이스130_청년(Y덤)`으로 잡히고 있었습니다. 이미 값이 있으면 유지하도록 고쳤습니다.

| | 수정 전 | 수정 후 |
|---|---|---|
| KT 연령 행 원본 연결 | 108 / 192 | **192 / 192** |
| KT 실제 요금제 수 | 122 | **38** |

## 26. KT 수집 범위를 2개 탭으로 축소 + 표 헤더 결합 버그

### KT는 이제 통합요금제 / 온라인전용(요고) 두 탭만 수집한다

`crawl_kt.TABS`에서 키즈/외국인·태블릿/스마트워치·기타를 뺐습니다. 캐시에는 5개 탭이

> 사이트에는 "전체" 탭(`filter_code=191, option_code=260`)도 있습니다. 라이브로
> 호출해 확인한 결과 **ItemCode 34개가 기존 5개 탭의 합집합과 정확히 동일**했습니다.
> 별도 상품이 없는 합쳐보기 뷰라 수집 대상이 아닙니다.

KT 254행(통합 241 + 요고 13). merge 쪽 `EXCLUDED_CATEGORIES`에서 KT 항목은 이제
필요 없어져 제거했습니다.

### 통합요금제 5개 ItemCode 라이브 대조 — 불일치 0

`1691 초이스더블` / `1681 초이스` / `1693 베이직` / `1694 베이직(이월)` / `1697 음성`을
실제 사이트와 대조했고, 요금·데이터·테더링·멤버십·혜택 목록 모두 일치했습니다.

### 표 헤더 결합 버그 (음성 18.7의 65+/75+덤 유실)

`flatten_headers()`가 컬럼명을 만들 때 **이미 확정된 다른 컬럼 이름**과 겹치는
텍스트를 걸러내고 있었습니다. 그래서 이런 표에서:

```
구분 | 월정액 | 음성 | 문자 | 65+덤 혜택 ─────────────────────────
                              데이터 제공 | 음성 | 문자 | 추가혜택
```

앞쪽에 이미 `음성`·`문자` 단독 컬럼이 있다는 이유로 하위 라벨이 지워져서,
`65+덤 혜택_음성`이 돼야 할 컬럼이 그냥 `65+덤 혜택`이 되고, 그 다음 칸은
상·하위 라벨이 **둘 다** 걸러져 이름이 비어 `col6`이라는 임시 이름을 받았습니다.
`col6`은 "덤" 문자열이 없어 연령 혜택 처리에서 통째로 무시됐습니다.

→ 컬럼마다 자기 상·하위 라벨끼리만 중복 제거하도록 고쳤습니다.
전수 스캔 결과 이 패턴에 걸리던 건 `1697(음성)`의 65+/75+덤 4개 컬럼뿐이었습니다.

덤으로 오는 `+30분`/`+50건`이 요금제 행에 반영되지 않던 것도 함께 고쳤습니다.
`음성`·`문자` 서브컬럼이 같은 분류로 묶여 컬럼명만으론 구분이 안 돼, 값에 붙은
단위(분/건)로 판단하도록 했습니다.

| | 수정 전 | 수정 후 |
|---|---|---|
| `음성 18.7` 65세 이상 | 100분 / 100건 | **130분 / 150건** |
| 혜택 행 | 2건 (300MB, +30분) | **4건** (+50건, 안심박스 추가) |

## 25. 수집 범위 축소 — 휴대폰 5G/LTE만, overage 컬럼 제거

### SKT의 network_gen이 통째로 하드코딩이었다

범위를 망 세대로 좁히려다 발견했습니다. `crawl_skt.py`가 `"network_gen": "5G"`로
**고정**하고 있어서 SKT 184행이 전부 5G로 찍혀 있었는데, 실제로는 이렇습니다.

| ledger 태그 (`supProdFltId=F01120`) | 실제 |
|---|---|
| 5G | 135행 |
| 3G | 28행 |
| LTE | 4행 |
| 태블릿/스마트 기기 | 11행 |
| (태그 없음 — 포켓파이·IoT·뉴태블릿) | 6행 |

즉 **3G·태블릿 45행이 5G로 위장**돼 있었습니다. 목록 API에는 망 정보가 없지만
`ledger`의 `prodFilterFlagList`가 정확히 주고 있었고, 이미 받아둔 캐시라
재크롤링 없이 고쳤습니다. `plan_category`도 `SKT-전체` 고정에서 `SKT-5G`/`SKT-3G`
처럼 실제 구분으로 바꿔, KT·LGU+와 같은 층위가 됐습니다.

### KT `3GB` → `3G` 오매칭

`_guess_network_gen`이 부분문자열로 찾아서 `데이터투게더 3GB`의 **`3GB`가 `3G`로**
걸리고 있었습니다. 세대 표기는 항상 괄호·공백으로 끊기므로 뒤에 영숫자가 오면
제외하도록 고쳤습니다.

> KT는 SKT와 달리 망 세대를 구조화해서 주지 않습니다. 현행 5G 주력인 `초이스`
> 상세 페이지에도 "5G"라는 문구가 **0회** 나옵니다. 그래서 KT만은 망 세대가 아니라
> **탭 분류**를 기준으로 거릅니다.

### 범위 필터

`merge_plans.py` 한 곳에서만 겁니다. `data/interim/`은 전부 그대로 남겨서,
범위를 다시 넓힐 때 재크롤링이 필요 없습니다.

```
KT-기타(구형 3G·피처폰·선불)  38    SKT-3G                 28
KT-태블릿/스마트워치           11    SKT-태블릿/스마트 기기   11
모요 network_gen=3G            3    SKT-미분류(포켓파이·IoT)  6
```

`KT-기타` 탭은 팀에서 값이 이상하다고 보고한 요금제(순완전무한·Style·알스마트·
알캡140·골든스마트150·손말·복지15000·웰컴선불 등)가 거의 전부 몰려 있던 곳입니다.
연령·자격 한정 요금제(키즈/청소년/청년/시니어/복지/외국인)는 정상적인 휴대폰
요금제라 **남겼습니다**.

### overage 컬럼 5종 제거

`overage_data_won_per_mb`, `overage_voice_won_per_sec`, `overage_sms_won_per_msg`,
`overage_video_call_won_per_sec`, `video_call_deduction_rate`를 스키마에서 뺐습니다.
`schema.parse_call_overage()`, `crawl_kt.parse_overage_footnote()`,
`crawl_moyo.parse_overage_rates()`도 함께 삭제했습니다. 소진 후 동작은
`data_throttle_speed`가 계속 나타냅니다.

## 12. "MNO 초과요금 312건 결측"은 **오진이었다**

앞서 이걸 "통신사가 공시를 안 해서 못 채우는 한계"로 적어 뒀는데, 실제 사이트를
직접 열어 확인해 보니 **틀린 진단이었습니다.**

**실사 결과 (캐시가 아니라 라이브 페이지 확인)**

| 통신사 | 확인한 요금제 | 데이터 소진 시 표기 |
|---|---|---|
| KT | 베이직110GB / 90GB / 600MB | `110GB +5Mbps`, `90GB +1Mbps`, `600MB +400Kbps` |
| SKT | 라이트 69 | `110GB + 최대 5Mbps` |
| LG U+ | 데이터플랜150GB | `150GB +다 쓰면 최대 5Mbps` |

KT 페이지에는 "초과"라는 **단어 자체가 없습니다.** 즉 **MNO는 데이터를 다 써도
추가 과금이 없고 속도만 제한**됩니다. `overage_data_won_per_mb`가 비어 있는 건
**결측이 아니라 "해당 없음"**이고, 소진 후 동작은 `data_throttle_speed`가 나타냅니다.

> 합성 사용량으로 청구액을 계산할 때: MNO 요금제는 데이터를 아무리 초과해도
> **데이터 요금이 0원**입니다. 월정액만 청구됩니다.

## 13. 테더링 값이 "줄 순서"에 의존하고 있었다

| | |
|---|---|
| **증상** | 겉보기엔 정상. 값도 맞음 |
| **원인** | LGU+ `공유 데이터` 칸 전체를 이어붙인 뒤 `to_gb()`로 **첫 번째 GB**를 집고 있었음 |
| **위험** | 이 칸에는 성격이 다른 두 값이 함께 온다 — `테더링+쉐어링 100GB`(내 회선 한도)와 `참 쉬운 가족 데이터 50GB`(가족 간 공유). 플러스플랜115는 **둘 다** 갖고 있는데, 100이 들어간 건 그저 **앞에 있어서**였다. 사이트가 순서를 바꾸면 조용히 50이 들어간다 |
| **수정** | 테더링/쉐어링 항목을 **명시적으로 골라서** 읽고, 가족 데이터는 의도적으로 제외 |
| **검증** | 수정 전후 `tethering_gb` **0행 변경** — 값은 그대로고 취약성만 제거됨 |

같이 정리한 것:

- **혜택명 접두사 중복 제거** — `공유데이터 테더링+쉐어링 100GB` → `테더링+쉐어링 100GB`
  (원문이 이미 무엇인지 말하고 있음). KT는 원문이 `100GB`뿐이라 `공유데이터` 접두사 유지
- **`tethering_gb`의 정의를 명세서에 못박음** — 이름은 "테더링"이지만 실제로는
  **테더링+쉐어링 통합 한도**이고, 가족 데이터 공유와 `데이터 쉐어링 N회선 할인`
  (용량이 아니라 회선 요금 할인)은 제외된다는 점을 표로 정리

### 찾은 실제 버그 2건

**(1) 요금제명 속 금액을 월정액으로 오인** — `무제한 7GB+1M(다이소 매월 5000원)`이

이름에 금액이 박힌 31건 전체가 정상화됐습니다.

**(2) 모요 프로모션 표기가 두 종류인데 하나만 처리** —
`혜택가 6개월간 월 7,000원 … 월 49,000원` 형태에서 **할인가를 정가로** 기록했습니다
(너겟49: 7,000원 → 실제 정가 49,000원). → 두 표기를 하나의 로직으로 통합.

이 과정에서 `discount_type`이 "페이백 포함"일 때만 채워지던 것도 고쳤습니다.
프로모션 할인가가 있는데 할인 종류가 비어 있던 **1,416행**이 채워졌습니다.

| 단위 환산 | `300MB`를 `0.293GB`로 저장했는데 페이지에서 `0.293GB`를 찾음 |
| 우리가 만든 값 | `요고 모바일 8GB`는 우리가 조립한 이름이라 페이지에 그대로 없음 |

**교훈**: 불일치가 나오면 **어느 쪽이 틀렸는지 원문으로 판정**하는 절차가 반드시
필요합니다. 그리고 이번 버그 2건이 모두 KT의
`"15,400원 (사회복지할인 35% 적용시 10,010원)"`과 **같은 부류**(텍스트에서 첫 숫자를
집는 방식)였습니다. 새 필드를 추가할 때는 **검색 범위를 먼저 좁히는 것**이 원칙입니다.

## 16. "첫 숫자를 집는" 패턴 전수 점검

버그 3건이 모두 같은 부류였기 때문에(`"15,400원 (사회복지할인…10,010원)"`,
`"다이소 매월 5000원"`, `"혜택가 6개월간 월 7,000원"`) 코드 전체에서 같은 방식을
쓰는 곳을 찾아 **실제 데이터로** 위험도를 측정했습니다.

위험 조건 = **앵커 키워드 없음** AND **대상 텍스트에 숫자가 2개 이상**

| 지점 | 숫자 2개 이상인 실제 사례 | 판정 |
|---|---|---|
| KT 덤 `영상/부가` 셀 (앵커 없음) | **0건** | 안전 |
| LG U+ 가격 엘리먼트 | **0건** | 안전 |
| SKT 음성/문자/데이터 API 필드 | **0건** | 안전 |
| KT 음성/문자 셀 (`분`/`건` 앵커 있음) | 4건 — 값 전부 정확 | 안전 |
| 모요 사은품명 (`_parse_krw`) | **133건** — 값 전부 정확하지만 **순서 의존** | 개선 |

`분`/`건`/`원/초` 같은 **단위 앵커가 있는 곳은 전부 정확**했습니다.
예: `"180분 (영상통화 1.66배 차감)"` → `(\d+)\s*분`이 180만 집음 (1.66은 `분`이 없어 무시).

### 개선한 것: 사은품 금액을 순서 무관하게

사은품명은 대체로 "총액(월별 분할)" 형태입니다.

```
네이버페이 19.2만원(매월 3.2만원씩)   -> 192,000
프레딧 쿠폰 2만원(5천원*4개월)        ->  20,000
M마켓 포인트 18만원 (2만원 X 9개월)   -> 180,000
```

기존 코드는 "만원 → 천원 → 원" 순서로 **첫 매치**를 썼습니다. 지금 데이터는 총액이
앞에 오므로 결과가 맞았지만(역순 사례 0건 확인), 사이트가
`"매월 3.2만원씩(총 19.2만원)"`처럼 어순을 바꾸면 **분할 금액을 총액으로 기록**합니다.
→ 등장 순서 대신 **가장 큰 금액**을 쓰도록 변경.

**검증: 사은품 금액 변경 0행** — 현재 값은 그대로 두고 취약성만 제거했습니다.

## 17. 경로 상수화 (실행 위치에 묶여 있던 문제)

| | |
|---|---|
| **증상** | 프로젝트 루트에서 실행할 때만 동작. 다른 폴더에서 돌리면 캐시를 못 찾거나 CSV가 엉뚱한 곳에 생김 |

## 18. 폴더 구조 분리

17번에서 경로를 한 곳에 모아 뒀기 때문에, 폴더 이동은 **상수 몇 줄 수정**으로 끝났습니다.

```
src/    schema.py  crawl_*.py  merge_plans.py
data/   raw_cache/<사이트>/   interim/   final/
docs/   컬럼_명세서.md  수정이력.md
README.md
```

### 왜 나눴나

루트에 19개 파일이 성격 4가지로 섞여 있었고, **중간 산출물과 최종 산출물이 구분되지
않는 것**이 가장 큰 문제였습니다. `kt_plans_final.csv`는 이름에 "final"이 있지만
중간 파일이라, 분석하는 사람이 최종본으로 착각하기 쉬웠습니다.

이참에 중간 산출물 이름도 정리했습니다.

| 이전 | 이후 |
|---|---|
| `kt_plans_final.csv` | `data/interim/kt_plans.csv` |
| `moyoplan_plans_full.csv` | `data/interim/moyo_plans.csv` |
| `통신요금제_*_최종.csv` | `data/final/통신요금제_*_최종.csv` |

`{사이트}_plans.csv` / `{사이트}_benefits.csv`로 규칙이 통일돼서 `merge_plans.py`도
파일명을 하나씩 나열하지 않고 사이트 목록으로 만들 수 있게 됐습니다.

### 검증

프로젝트와 무관한 디렉터리에서 크롤러 4개 + `merge_plans.py`를 실행:

```

최종 2769/4172   고유 plan_id 2769   고아 0
```

행 수 전부 동일(**회귀 없음**), 실행 디렉터리에 생긴 파일 0개,
`data/raw_cache` 3,141개 파일(533MB) 전부 이동 확인.

## 21. SKT 청년 혜택(만 34세 이하) — 연령 행 확장

### 연령 구분은 "만 34세 이하" 하나가 맞다

처음엔 청소년(≤18)/청년(19~34)/시니어(≥65) 3분할로 보였는데, 전수 조사하니
**대부분은 "청년 혜택(만 34세 이하)" 하나**였습니다.

| 구성 | 요금제 수 |
|---|---|
| `청년 혜택`(만 34세 이하)만 | **39** |
| 청년 + 청소년 세분 | 7 |
| 청년 + 청소년 + 시니어 | 5 |
| 시니어만 | 2 |

세분이 있는 12개도 상위 라벨이 "청년 혜택(만 34세 이하)"라서, 그 하나로 묶었습니다.

### 값의 소재가 두 가지

| 형태 | 건수 | 예 |
|---|---|---|
| **표** (베스트 계열) | 22 | `요금제 \| 기본 공유/테더링 한도 \| 청년(만 34세 이하) 한도` → 140GB→160GB |
| **문장** (라이트 계열) | 11 | `기본 데이터 50GB 추가 제공` |
| 수치 없음 | 43 | 커피/영화/로밍 할인만, 제공량 변화 없음 |

> **표 구간을 좁히는 게 필수였습니다.** 표에는 여러 요금제가 함께 나열되는데,
> 구간 제한 없이 "요금제명 + 숫자 두 개"로 찾으면 **다른 표**(기본 제공량 등)를
> 잘못 집습니다. 실제로 처음 시도에서 `다이렉트5G 38`이 `15GB → 15GB`(증가 없음)로
> 나왔고, `청년 혜택 안내표` 이후 구간으로 한정하니 22건 전부 정상(오매칭 0건)이 됐습니다.

### 설계: 제공량이 늘어나는 것만 행 확장

- **제공량 증가 33건** → KT 덤과 같은 방식으로 연령 변형 행 생성
  (`base_tethering_gb=140`, `extra_tethering_gb=20`, `tethering_gb=160`)
- **할인만 있는 43건** → 스펙이 그대로여서 행을 늘리면 같은 스펙 두 줄이 되므로
  **혜택 행으로만** 기록

또한 **이미 연령 제한이 걸린 요금제**(`0 청년 다이렉트`=34세 이하 전용,
`ZEM플랜`=키즈 전용)는 그 자체가 연령 상품이라 또 나누지 않습니다.

### 수정 중 잡은 자체 버그

혜택 문구를 커피/영화/로밍 **각각의 정규식**으로 찾았더니 같은 문구를
`커피/영화/로밍 50% 할인`, `영화/로밍 50% 할인`, `로밍 50% 할인` 세 번 잡아
혜택이 3배로 부풀었습니다(325건). 슬래시 목록을 통째로 한 번에 잡도록 고쳐
177건으로 정상화했습니다.

## 22. 연령 혜택 일반화 — 시니어 추가, 청소년/청년 분리, 라벨별 파싱

21번을 시니어까지 확장하려고 원문을 다시 읽다가 **21번 코드의 결함을 발견**했습니다.

### 문장 정규식이 라벨을 무시해 청소년 값을 청년 값으로 기록했다

`라이트 39` 원문:

```

시니어 혜택(만 65세 이상) 기본 데이터 1.5GB 추가 제공
```

본문 전체에서 첫 매치를 집었더니 **청소년 값 1.5GB**를 청년 값으로 기록했습니다

라벨로 쪼갠 뒤 각 라벨의 값만 파싱. 이 블록이 요금제별 연령 혜택의 권위 있는 출처입니다.

### 시니어(만 65세 이상) 5개 요금제 추가

> 표도 탭 라벨도 없는 331개는 모요 비제휴/타사 안내 페이지("신청 페이지로 이동")라서
> 원래 해당 섹션이 없습니다. 재수집 대상이 아닙니다.

### 신고 중 사실이 아니었던 것

- **테더링 `월 11GB 이용 가능`**(35324): 이미 정상 파싱됨(`tethering_gb=11.0`).
  27457은 캐시 불완전 문제였습니다.
- **36218 `data_gb=11`이 이름의 71GB와 다르다**: 원문이 `월 11GB + 매일 2GB + 3Mbps`이고
  `daily_data_gb=2.0`도 채워져 있습니다. "무제한71GB"는 11 + 2×30 마케팅 표기 — **정상**.

## 24. LG U+ 데일리플러스 — 두 번째 택1 그룹 누락

`너겟75`의 택1 옵션이 1개뿐인 게 이상해서 원문을 확인했습니다.

- `프리미엄플러스(택1)`가 `삼성디바이스` 하나인 건 **원문도 그렇습니다**(요금제별 안내표에
  `너겟75 → 삼성디바이스`로 단독 표기). 누락이 아닙니다.
- 대신 그 아래에 **`데일리플러스 5개 중 택1`**(구글원 / 모아진 / 교보문고 sam / 지니뮤직 /
  밀리의 서재)이라는 별개 택1 그룹이 있었고, **전혀 수집되지 않고 있었습니다.**

프리미엄플러스는 `premium-benefit` API로 받는데 데일리플러스는 API에 없고 상세페이지에만
있어서 통째로 빠졌습니다. 6개 요금제 × 5개 옵션을 혜택 행으로 추가했습니다
(선택지가 5개로 프리미엄플러스보다 적어, "가장 큰 그룹만 전개" 규칙에 따라 행은 안 늘림).

## 19. LGU+ 너겟 / 모요 상세페이지 — 실제 사용자 신고로 발견

사용자가 "LGU+ 너겟과 모요에 같은 요금제(너겟49)가 있는데 혜택이 다르다"고
직접 비교해서 신고한 것을 계기로 두 소스를 나란히 대조했습니다.

### 19-1. LGU+ 너겟: 소진 후 속도(`+다 쓰면 최대 5Mbps`)가 통째로 빠짐

| | |
|---|---|
| **잘못된 전제** | 코드 주석에 "너겟은 상세 페이지에 스펙이 없어 목록 카드로 파싱"이라 적혀 있었음 |
| **실제** | 상세 페이지에 스펙 패널이 **있음**(`li.plan-list__item`). 목록 카드엔 `데이터 120GB`까지만 있고 `+다 쓰면 최대 5Mbps`가 없어서, 카드만 보면 소진 후 속도가 유실됨 |

### 19-2. LGU+ 너겟 URL 재구성 버그 (2차 발견)

| | |
|---|---|
| **증상** | 19-1을 고쳐 상세 수집을 켜자, 너겟65/59/69/75와 LTE 다이렉트22의 **이름·요금이 통째로 빔** |
| **원인** | `collect_direct_codes`가 클릭 후 URL의 **마지막 조각(상품코드)만** 저장하고 `/direct/nerget/{code}`로 재구성. 실제 경로가 3종류였음: `/direct/nerget/…`(7개) / `/direct/nergetunlimited/…`(4개) / `/direct/lte-direct/…`(1개). 경로가 다른 5개는 엉뚱한 일반 목록 페이지가 저장됨 |
| **수정** | URL 전체를 저장하도록 변경. 회귀 방지로 `_looks_like_detail_page()` 가드 추가(제목+스펙 패널 확인, 없으면 카드로 폴백) |

### 19-3. 모요: 핫스팟 GB, 부가통화 분수가 상세페이지에만 있음

목록 카드에는 테더링·부가통화 정보가 아예 없고, 상세페이지 `지원`/`부가통화` 항목에만
있었습니다. `월 60GB 이용 가능`(→60) vs `데이터 제공량 내 이용 가능`(→빈값),
`부가통화 300분`(→300) vs `제공 안 함`/`통신사 문의`/`제공량 내`(→빈값)로 구분.

### 19-4. 두 소스 대조 중 발견한 LGU+ 자체 버그 3건

| 버그 | 규모 | 내용 |
|---|---|---|
| `voice_unlimited` 오판정 | 12건 | 음성이 `무제한`/`기본제공` 두 표기인데 `무제한`만 인정. 문자는 `기본제공`을 인정하는데 음성만 안 됨 |
| `voice_minutes` 유실 | 20건 | 하드코딩 빈값. `집/이동전화 125분`이 전부 버려짐 |
| `sms_count` 유실 | 17건 | 하드코딩 빈값. `문자 250건`/`150건`이 전부 버려짐 |

### 검증

너겟49를 두 소스(LGU+ 직영 vs 모요 등록)로 나란히 비교, 핵심 스펙 전부 일치:

```
monthly_fee 49000=49000   data_gb 120=120   throttle 5Mbps=5Mbps
tethering_gb 60=60   voice_unlimited True=True   voice_extra_minutes 300=300
```

남은 차이(`discounted_fee`)는 버그가 아니라 판매 채널(직영 vs MVNO 등록) 차이.

## 20. "숨은 데이터" 전체 점검 — 하드코딩된 빈값을 실마리로

19번에서 찾은 패턴("원문엔 있는데 우리가 안 읽는 필드")이 다른 곳에도 있는지
**4개 크롤러 전체에서 빈 문자열 하드코딩 지점을 grep**해서 하나씩 원문을 대조했습니다.

### 20-1. KT `요고` — 실제 상품 13개가 전부 가짜 이름으로 대체돼 있었음 (가장 큼)

| | |
|---|---|
| **증상** | `요고 모바일 8GB`처럼 우리가 만든 이름, 혜택 0건 |
| **원인** | `요고` 페이지(item 1567)에 **실제 이름이 있는 정식 표**(요고69/61/55/49/46/44/42/40/38/36/34/32/30)가 있는데, 코드가 이걸 무시하고 UI용 "가격 계산 슬라이더"(`#volume`/`#month`)만 파싱해서 합성 이름의 요금제를 만들고 있었음 |
| **검증** | 슬라이더의 용량·가격 쌍(`8GB=3만원`, `무제한=6.1만/6.9만`)이 정식 표의 요고30~69와 **완전히 일치** — 같은 상품을 보여주는 다른 UI였을 뿐, 별개 상품이 아님 |
| **수정** | 슬라이더 특수 케이스(`SLIDER_ITEM_CODES`, `parse_slider_variants`, `_parse_korean_price`)를 전부 제거하고 다른 KT 요금제와 같은 표 파싱 경로로 합침 |

**결과**: 13개 요금제 전부 실명 + 정확한 소진 후 속도(5Mbps/1Mbps/400Kbps) +
부가통화 300분 + 스마트기기/멤버십/초이스/플러스 혜택이 살아남.
덤으로 원문의 "요고Y덤"(만 34세 이하 데이터 2배) 혜택도 새로 추가함.

> 데이터 헤더가 "데이터_기본 제공"/"데이터_요고Y덤"으로 갈라져 있어서
> (다른 KT 표는 그냥 "데이터"), `table_row_to_unified`의 데이터 추출에
> `_find_col` 폴백을 추가해야 했습니다.

### 20-2. SKT — MB 단위로만 오는 소용량 요금제 13개의 데이터가 전부 빈값

| | |
|---|---|
| **증상** | `주말엔 팅 세이브`, `T끼리 어르신` 등 13개 요금제의 `data_gb`가 빈값 |
| **원인** | API가 데이터를 `basOfrGbDataQtyCtt`(GB)와 `basOfrMbDataQtyCtt`(MB) **두 필드**로 나눠 주는데, 코드가 GB 필드만 읽음. 이 13개는 소용량이라 MB 필드에만 값이 있었음 |
| **주의** | 이 필드에 `함께쓰기`처럼 숫자가 아닌 값(데이터 나눠쓰기 부가상품)도 섞여 있어 숫자인지 먼저 확인 후 사용 |
| **결과** | 4개 샘플 확인: 800→0.781GB, 400→0.391GB, 250→0.244GB, 50→0.049GB |

### 20-3. LGU+ 카드 폴백 파서의 잔여 버그

19-4에서 고친 `voice_minutes`/`sms_count` 하드코딩 빈값이 상세페이지 파서
(`parse_detail`)에만 반영되고, 상세 실패 시 쓰는 **카드 폴백 파서**

파싱돼 폴백이 거의 안 쓰이지만, 안전망이 고장 나 있으면 의미가 없어 같이 고침.
