# 사용자 세그먼트 설계 및 합성 고객 데이터

팀 노션에 정리된 설계(고객/이용량/가입정보 테이블 + 연령세그먼트 + 이용형태세그먼트
S1~S6)를 채택했다. 이전에 만든 6종 페르소나 기반 설계(`docs/페르소나_설계.md`)는
이 문서로 대체됐다 - "일단 S1~S6로 진행하고 이후 필요하면 세분화하자"고 정했다.

## 왜 파일을 3개로 나눴는가

처음엔 2개(고객+이용량)로 나눴는데, `ott_preference`를 고객 테이블에 넣어두고 보니
사용자가 "이거 통신사가 사전에 알 수 없는 사후 데이터 아니냐"고 지적했다. 맞는
지적이었다 - **"통신사가 이미 갖고 있는 관측 데이터"와 "상담 시점에 사용자가
그 자리에서 답하는 값"은 근본적으로 다른 데이터**인데 한 테이블에 섞여 있었다.
OTT 선호를 통신사가 미리 알 방법은 없다(가입한 요금제에 이미 넷플릭스가
번들돼 있다면 그건 "혜택"이지 "선호"가 아니다). 대신 기획서상 User Profiling
Agent가 상담 시점에 실시간으로 수집하는 값이 바로 이거다 - 즉 가짜라서 빼야 할
데이터가 아니라, **"합성 데이터를 만드는 우리가 상담을 진행했다고 가정하고 만든
설문 응답"**으로 성격을 명확히 하고 별도 테이블로 옮겨야 하는 데이터였다(팀
노션의 "사용자 선호도 테이블 [사후데이터]"가 정확히 이 개념).

그래서 최종적으로 3개다. 이용량 테이블을 따로 뗀 이유는 원래 이유 그대로 -
요금제 데이터를 plans/benefits 2개로 나눈 것과 같은 이유(1대1 관계와 1대다
관계를 같은 파일에 억지로 넣지 않는다)다.

| 파일 | 관계 | 내용 |
|---|---|---|
| `data/synthetic/synthetic_customers.csv` | 고객 1명 = 1행 | **통신사가 실제로 갖고 있을 법한 사실만** - 나이·이용형태세그먼트·현재 가입정보(가입정보는 고객과 1대1이라 따로 안 나눔) |
| `data/synthetic/synthetic_usage_monthly.csv` | 고객 1명 x 3개월 = 3행 | 이용량(1대다 관계) |
| `data/synthetic/synthetic_preferences.csv` | 고객 1명 = 1행 | **상담 시점 입력을 시뮬레이션한 값** - OTT 선호, 다음 요금제 통신사 선호, 필수조건(데이터/음성/문자 무제한), 약정 허용 여부, 현재 요금제 만족도, 선호 망세대, 희망 최소 소진속도 |

`preferences`의 "다음 요금제로 원하는 통신사"는 `customers`의 "지금 가입돼 있는
통신사"(연령대별 실제 시장 분포로 배정됨)와 다른 개념이다 - 같은 사람이 지금은
MNO를 쓰지만 다음엔 MVNO로 갈아타고 싶어할 수 있어서, 두 값이 독립적으로
샘플링된다.

**`current_plan_satisfaction`은 `customers.assignment_intent`(아래 참고)와
상관관계를 줬다** — 부족하게 배정된 고객의 만족도가 실제로 낮게 나오는지가
합성 데이터의 현실성을 가르는 지점이라서다. 검증 결과: `good` 평균 3.97 /
`over` 평균 2.98 / `shortage` 평균 2.04로 의도한 순서대로 정확히 갈렸다.

팀 설계에 있던 "3개월 요약 VIEW"/"적합도 VIEW"는 파일로 안 만든다. SQL VIEW가
저장되는 테이블이 아니라 조회 시점에 계산되듯, 이것도 분석/에이전트 코드에서
`usage_monthly.groupby('customer_id').agg(...)`로 그때그때 계산한다.

## 연령세그먼트

경계는 임의로 정하지 않고 실제 요금제 데이터의 `age_condition` 정규화 기준
(`schema.normalize_age_condition`)에 맞췄다 — 그래야 "가입 가능 요금제 필터링"이
실제 데이터와 어긋나지 않는다.

| 세그먼트 | 연령 | 전체 인구 비중 | 근거 |
|---|---|---|---|
| CHILD | 6~12세 | 4% | 본인 명의 개통이 드묾 |
| TEEN | 13~18세 | 8% | 중고생 |
| YOUTH | 19~34세 | 28% | 자취생·사회초년생 등 통신 소비 활발 |
| GENERAL | 35~64세 | 42% | 경제활동인구 핵심층, 가장 큰 덩어리 |
| SENIOR | 65~85세 | 18% | 고령화로 절대 수는 적지 않되 청년/일반보다는 낮게 |

(비중은 실측 통계가 아니라 가정 — 사용자가 "CHILD/SENIOR는 낮아야 하지 않나"라고
지적해 반영한 값. 나중에 실측 근거가 생기면 교체할 것)

**"현재 가입된 통신사"의 연령세그먼트별 시장 분포를 다르게 뒀다** (`customers.csv`
생성용, `preferences.csv`의 OTT/통신사 선호와는 별개 - 위 "왜 파일을 3개로
나눴는가" 참고). 연령 조건부 요금제(청년 덤·시니어 특화·키즈)가 노트북 EDA상
전량 MNO였으므로, 그 조건을 쓸 법한 세그먼트일수록 비율을 높였다(CHILD 75% ·
TEEN 70% · SENIOR 65% vs GENERAL 45%).

## 이용형태세그먼트 S1~S6 (팀 설계 그대로)

| 세그먼트 | 데이터 | 통화 | 문자 | 테더링 |
|---|---|---|---|---|
| S1 저사용 절약형 | 0.5~8GB | 30~200분 | 5~80건 | 0~2GB |
| S2 일반 균형형 | 8~30GB | 100~400분 | 10~150건 | 0~8GB |
| S3 데이터 헤비형 | 40~150GB | 50~350분 | 5~100건 | 5~30GB |
| S4 통화집중 저데이터형 | 1~10GB | 500~2,000분 | 30~300건 | 0~3GB |
| S5 통화집중 균형형 | 10~40GB | 500~2,000분 | 30~300건 | 0~10GB |
| S6 업무 헤비형 | 50~200GB | 500~2,000분 | 30~500건 | 20~100GB |

**연령세그먼트별로 이용형태 확률을 다르게 줬다**(완전 무작위 조합 방지 - "8세
아이가 업무헤비형"은 안 나오게). CHILD/TEEN/SENIOR는 S3(데이터헤비형)·S6(업무헤비형)
확률이 0이고, SENIOR는 S4(통화집중저데이터형) 비중이 높다(통화는 많고 데이터는
적은 실사용 패턴 - 이전 페르소나 설계 때 EDA로 확인한 것과 동일).

## 현재 가입 요금제 배정 — 전체 시나리오의 성패가 갈리는 지점

무작위로 배정하면 비현실적이고, 이용형태에 딱 맞게 배정하면 다들 적합 판정이
나와서 추천할 이유가 없어진다. 그래서 **의도적으로 배정 품질을 섞는다**
(`ASSIGNMENT_MIX` — good 60% / shortage 20% / over 20%). 배정 로직:

1. 나이 자격 조건(연령 조건부 요금제 상한/하한)을 만족하는 요금제만 후보로
2. 선호 통신사로 좁히되, 후보가 없으면(예: CHILD가 MVNO 선호인데 키즈 요금제는
   MNO뿐인 경우) 전체 자격 풀로 폴백
3. 이용형태세그먼트의 "필요 데이터량"(구간 중간값)을 기준으로 good/shortage/over
   구간에서 하나를 뽑음

배정 의도는 `assignment_intent` 컬럼에 **정답 라벨로 남겼다.** 실제 서비스라면
알 수 없는 값이지만, 이 데이터는 적합도 판정 로직(팀 설계의 `OVERPROVISIONED`~
`REPEATED_SHORTAGE`)을 검증하기 위한 것이므로 정답을 같이 둬야 "판정 로직이
의도한 대로 잡아내는지" 확인할 수 있다. **적합도 판정·추천 로직 자체는 이 컬럼을
읽으면 안 된다** — 읽으면 답을 미리 보고 채점하는 것과 같다.

검증 결과(S3 데이터헤비형, 필요량 ~95GB 기준):

```
good     : 평균 114.2GB (필요량보다 살짝 위, 무제한 0건)
over     : 무제한 59건 + 유한 평균 300GB (확실히 과함)
shortage : 평균 18.8GB (확실히 부족)
```

## 3개월 이용량 생성

고객마다 세그먼트 구간 내에서 개인 기준값을 하나 뽑고, 매달 ±25% 흔든다(3개월이
전부 똑같으면 3개월치를 만든 의미가 없다). 10%는 한 달만 크게 튀는(1.8배) 고객으로
만들어 `PEAK_SHORTAGE`류 시나리오가 실제로 나오게 했다.

## 검증

`python src/analysis/generate_synthetic_customers.py --validate`

```
고객 3,500행 + 이용량 10,500행 + 선호 3,500행 = 총 17,500행 ("1만 행 이상" 요건 충족)
연령x이용형태 교차표: CHILD/TEEN/SENIOR는 S3/S6 0건 확인
배정 의도 분포: good 60% / over 19% / shortage 21% (설계값과 근접)
만족도-배정의도 상관관계: good 3.97 / over 2.98 / shortage 2.04 (의도한 순서대로 갈림)
두 번 재실행 결과 바이트 단위 동일 (재현성)
```

기반 세그먼트를 뽑고, 여기 S1~S6/연령세그먼트와 대조한다. Plan Matching Agent를
