# 멀티에이전트 설계 노트

기획서(ASAC/SKB)가 요구하는 7개 에이전트의 구현 현황과, 실제로 겪은 문제에서
필요성이 드러난 **추가 에이전트**를 기록해 둡니다.

## 현재 구현 상태

| 에이전트 | 상태 | 위치 |
|---|---|---|
| ① Orchestrator | 미구현 | — |
| ② User Profiling | 미구현 | — |
| ③ **Data Retrieval** | **구현됨** | `src/agents/data_retrieval_agent.py` |
| ④ Usage Prediction / Segmentation | 미구현 | — |
| ⑤ Plan Matching & Ranking | 미구현 | — |
| ⑥ Explanation & Report | 미구현 | — |
| ⑦ Evaluation / Feedback | 미구현 | — |
| ⑧ **Schema Drift Detection** (아래) | **구현됨 (독립 노드 아님)** | `src/agents/schema_drift.py` |

그래프는 `src/agents/graph.py`에 `START -> data_retrieval -> END` 1노드로만
연결돼 있습니다. 노드를 추가할 때는 `AppState`(`state.py`)에 그 노드가 채우는
필드를 먼저 정의하고, `builder.add_node` / `add_edge`로 이어 붙입니다.

---

## ⑧ Schema Drift Detection Agent (구조변경 감지)

### 왜 필요한가 — 실제로 데이터가 조용히 망가졌다

2026-08-03 갱신에서 KT가 요금표 데이터를 페이지 안 `<script>`에서 **외부 JS
파일로 옮겼습니다**(`docs/수정이력.md` 35번). 크롤러는 그 파일을 받지 않으니
주력 4개 상품이 통째로 0건이 됐고, KT는 259행 -> 29행(-89%)이 됐습니다.

문제는 **에러가 하나도 안 났다**는 점입니다. HTTP 200, 파싱 예외 없음, 크롤러
종료코드 0. 데이터만 조용히 사라졌습니다. 게다가 그때의 가드는 전체 행 수만
봐서(모요가 8할이라 전체로는 -8%) 그냥 통과했고, **망가진 데이터가 최종 CSV에
반영됐습니다.** 사람이 리포트를 열어보고서야 발견했습니다.

지금은 두 가지로 대응해 뒀습니다.

1. **수집 단위별 급감 가드**(`refresh_plans.MAX_SITE_DROP_RATIO = 0.35`) —
   한 사이트가 35% 넘게 줄면 최종 CSV를 안 건드리고 중단합니다.
2. KT의 외부 JS는 파일명을 하드코딩하지 않고 `js/data/*.js` **패턴**으로 찾게
   해서, 같은 구조를 쓰는 다른 상품은 자동으로 따라갑니다.

하지만 이건 **"망가진 걸 알아채고 멈추는"** 데까지입니다. 무엇이 어떻게 바뀌었고
어떻게 고쳐야 하는지는 여전히 사람이 원본 HTML을 뒤져서 알아내야 합니다. 이번에도
"tableHTML이 외부 JS로 빠졌다"를 찾는 데 대부분의 시간이 들었습니다.

### 이 에이전트가 할 일

가드가 걸렸을 때(또는 특정 사이트 수집량이 급감했을 때) 자동으로 원인을 조사해
**사람이 읽을 진단 리포트**를 만듭니다.

1. 문제가 된 사이트의 **이전 캐시 HTML과 현재 HTML을 비교**한다
   (`data/raw_cache/`에 원본이 그대로 남아 있어 가능).
2. 파서가 의존하는 앵커(`tableHTML`, CSS 셀렉터, API 응답 키 등)가 **아직
   존재하는지** 확인한다.
3. 없어졌다면 LLM에게 새 HTML 구조를 보여주고 *"원래 이 데이터가 여기 있었는데
   지금은 어디에 있는가"*를 묻는다.
4. 추정 원인 + 근거가 되는 HTML 조각 + 제안하는 수정 방향을
   `data/review/drift_YYYY-MM-DD.md`로 남긴다.

### 자율적으로 어디까지 맡길 것인가 — 선을 그어야 한다

**파서 코드를 에이전트가 스스로 고쳐서 반영하게 두면 안 됩니다.** 이번 사고의
교훈이 정확히 그것입니다. 이 프로젝트에서 이미 두 번, *"몇 개 사례만 보고
일반화한 수정"*이 새로운 오류를 만들었습니다(`수정이력.md` 34번의 모요 가격
되돌림, 15번의 검증 스크립트 오탐). LLM이 HTML 몇 조각을 보고 만든 셀렉터는
같은 종류의 실수를 **더 빠르고 조용하게** 저지릅니다.

| 단계 | 자율 실행 | 이유 |
|---|---|---|
| 이상 감지 | ✅ | 이미 가드가 수치로 판정. 판단 여지 없음 |
| 원인 조사·구조 비교 | ✅ | 읽기만 함. 틀려도 리포트가 틀릴 뿐 데이터는 안전 |
| 수정 방향 제안 | ✅ | 사람이 검토할 초안 |
| **파서 코드 수정** | ❌ | 조용히 틀린 값을 넣을 위험. 사람 검토 필수 |
| **최종 CSV 반영** | ❌ | 이미 가드가 막고 있음. 에이전트가 뚫으면 가드가 무의미 |

즉 **"고치는 에이전트"가 아니라 "원인을 찾아 보고하는 에이전트"**로 설계합니다.
사람의 진단 시간을 줄이는 것이 목적이고, 반영 여부는 사람이 정합니다.

### 구현 방식 — 독립 노드가 아니라 Data Retrieval이 호출한다

별도 그래프 노드로 만들지 않고, `data_retrieval_agent.diagnose_drift()`가
`schema_drift` 모듈을 부르는 형태로 넣었습니다. 이유는 두 가지입니다.

- **감지는 이미 Data Retrieval 안에 있습니다.** `check_guards()` 결과를 받아
  `data_stale_aborted`로 내보내고, `validate_output()`으로 매번 구조 검증도
  합니다. 노드를 새로 만들면 이 판정을 두 곳에서 하게 됩니다.
- **지금 진단은 LLM을 안 씁니다.** 파일 목록과 집합 연산뿐이라 빠르고
  결정적이라, 매일 도는 스케줄러 안에서 돌려도 부담이 없습니다.

나중에 LLM 기반 원인 추론(“이 앵커가 어디로 갔는지 HTML을 읽고 설명”)을 붙이면
성격이 달라지므로 — 느리고, 비결정적이고, API 키가 필요해집니다 — 그때 독립
노드로 승격하는 게 맞습니다. 그 시점의 그래프 배선은 이렇게 됩니다.

```python
builder.add_conditional_edges(
    "data_retrieval",
    lambda s: "schema_drift" if s["drift_regressed"] else "user_profiling",
)
builder.add_edge("schema_drift", END)   # 진단 리포트만 남기고 종료
```

`AppState`에 추가된 필드(`state.py`):

```python
drift_report_path: str      # 진단 리포트 경로. 회귀가 없으면 빈 문자열
drift_regressed: dict       # {사이트: [파싱 안 된 소스 키]}
```

### 어떻게 판정하는가 — 절대값이 아니라 기준선 대비

처음엔 “캐시에는 있는데 CSV에 없는 파일”을 그냥 셌는데, **KT 35개 중 27개가
잡혀서 신호가 잡음에 묻혔습니다.** 수집 범위 밖이라 일부러 안 쓰는 캐시가
많기 때문입니다(KT는 예전 5개 탭을 받아뒀지만 지금 3개만 쓰고, SKT는 147개 중
50개만 씁니다).

그래서 `data/review/parse_coverage.json`에 **“마지막으로 멀쩡했을 때 어떤
소스에서 행이 나왔는지”**를 기준선으로 남기고, 그때는 나왔는데 지금은 안 나오는
것만 회귀로 봅니다. 범위 밖 캐시는 애초에 기준선에 없으므로 조용합니다.

> **회귀가 감지되면 기준선을 갱신하지 않습니다.** 갱신해버리면 다음 실행부터
> 망가진 상태가 “정상”이 돼서 같은 문제를 다시는 못 잡습니다.

검증(KT 사고 재현): 기준선 8개 소스 → 4개만 파싱되는 상황을 만들자
`1681/1692/1693/1694` 정확히 4건을 회귀로 검출했고, 정상 상태에서는 오탐 0건.

### 남은 설계 질문

- **LLM 원인 추론을 붙일 것인가.** 지금은 “앵커가 사라졌다”까지만 알려주고
  “어디로 갔는지”는 사람이 찾습니다. HTML 한 페이지가 수십 KB라 통째로 넣기
  어려워서, 앵커 주변만 잘라 보내는 전처리가 필요합니다.
- **이전 캐시를 어떻게 확보하나.** 지금은 커버리지(소스 키 목록)만 기준선으로
  두고 HTML 자체는 비교하지 않습니다. “예전 HTML과 지금 HTML의 구조 차이”까지
  보려면 직전 캐시가 필요한데, 모요만 569MB라 전부 이중 보관은 무리입니다.
- **오탐 — 실제 개편과 파싱 실패의 구분.** 이번 KT 건은 둘이 **동시에**
  일어났습니다(요금표가 외부 JS로 이동 + 초이스 더블 1종→4종 개편). 기준선
  방식이 전자는 잘 잡지만, 상품이 진짜로 단종된 경우도 회귀로 보일 수 있습니다
  (캐시가 남아 있는 동안만). 리포트를 사람이 보고 판단해야 하는 이유입니다.
