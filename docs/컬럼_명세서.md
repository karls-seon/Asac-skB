# 통신요금제 데이터 컬럼 명세서

4개 사이트(KT / SKT / LG U+ / 모요)에서 수집한 요금제·혜택 데이터의 컬럼 정의서입니다.
`schema.py`의 `PLAN_COLUMNS` / `BENEFIT_COLUMNS`와 1:1로 대응합니다.

## 파일 구성

| 파일 | 내용 | 행 단위 |
|---|---|---|
| `data/final/통신요금제_통합데이터_최종.csv` | 요금제 | 요금제 1개 (택1 선택지까지 펼친 것) = 1행 |
| `data/final/통신요금제_혜택상세_최종.csv` | 혜택 | 요금제 1개 × 혜택 1개 = 1행 |
| `data/final/통신요금제_가입자일별_최종.csv` | 일별 가입자 추이 (**알뜰폰만**) | 요금제 1개 × 날짜 1일 = 1행 |

### 수집 범위: 휴대폰 5G/LTE 요금제

최종 CSV에는 **휴대폰용 5G·LTE 요금제만** 들어갑니다. 태블릿·스마트워치, 3G,
선불폰 요금제는 스펙 구조가 달라(음성/문자가 아예 없거나 공유회선 전용) 추천
모델에서 이상치로 작동하므로 제외했습니다. **연령** 한정 요금제(키즈/청소년/
청년/시니어)는 정상적인 휴대폰 요금제라 **남아 있고** `age_condition`으로
구분됩니다. **외국인·복지** 전용은 나이와 달리 서류·자격 확인이 필요해
일반 추천 대상이 아니므로 **제외**했습니다.

### 무엇을 빼고 무엇을 남기는가

기준은 **스펙 구조가 같은가**입니다.

| | 처리 | 이유 |
|---|---|---|
| 태블릿·스마트워치·3G·선불폰 | **제외** | 음성/문자가 없거나 종량 과금이라 **스펙 구조 자체가 다름**. 같은 테이블에 두면 이상치로 작동 |
| 데이터 미제공(음성전용) | **제외** | KT `음성 12.1`·SKT `표준요금제` 등 19행. 데이터를 아예 안 줘서(원문 `-`, "데이터 사용 기본차단") 휴대폰 요금제 추천 대상의 스펙 구조가 아님. 값이 싸다는 이유만으로 상위에 올라오던 것들 |
| 연령 전용 (키즈·청소년·유쓰·시니어) | **유지** | 5G 휴대폰 요금제로 **스펙 구조는 동일**하고 가입 자격만 다름. `age_condition`으로 걸러 쓰면 됨 |
| 외국인·복지 전용 | **제외** | 나이와 달리 **서류·자격 확인**이 필요해 일반 추천 대상으로 부적합 |

연령 전용을 빼면 만 25세 사용자에게 실제로 가장 유리한 유쓰 요금제를 영영 추천할 수
없게 됩니다. 게다가 3사 중 한 곳만 빼면 *"청년용은 LGU+에만 있다"* 는 편향이 생깁니다.

## ⚠️ 먼저 알아야 할 3가지

### 1. 빈 칸의 의미는 컬럼마다 다릅니다

빈 칸이 항상 "데이터 누락"을 뜻하지 않습니다. 아래 세 가지가 섞여 있습니다.

| 의미 | 예시 |
|---|---|
| **해당 없음** | `data_gb`가 비었는데 `data_unlimited=True` → 무제한이라 GB 개념이 없음 |
| **사이트 미공시** | KT의 `benefit_value_won` → KT가 혜택 금액을 공개하지 않음 |
| **개념 자체가 없음** | 멤버십 VVIP의 `benefit_value_won` → 등급 혜택은 금액으로 환산 불가 |

**특히 `benefit_value_won`은 전체의 약 1/3만 채워져 있습니다.** 모델 피처로 쓸 때
결측 처리를 일괄로 하면 안 되고, `benefit_category`와 함께 봐야 합니다.

### 2. "요금제 개수"는 행 수가 아니라 `base_plan_id`로 세야 합니다

택1(선택형) 혜택이 있는 요금제는 **선택지마다 별도 행**으로 펼쳐져 있습니다.

```
행 수                     = 고를 수 있는 조합의 수
nunique(base_plan_id)     = 실제 요금제의 수
```

### 3. 금액 단위는 전부 **원(KRW)**, 데이터 단위는 전부 **GB**입니다

MB로 표기된 원문(600MB 등)도 GB로 환산해서 저장합니다 (`600MB` → `0.586`).

## 요금제 테이블 (`통신요금제_통합데이터_최종.csv`)

### 식별

| 컬럼 | 타입 | 설명 | 빈값일 때 |
|---|---|---|---|
| `carrier_type` | 범주 | `MNO`(통신 3사) / `MVNO`(알뜰폰) | 없음 |

> **모요는 알뜰폰만 파는 게 아니라 통신 3사 자사 온라인전용 상품(너겟/요고/다이렉트)도
> 그대로 중개합니다.** 이런 행은 모요 상세페이지 `<title>`의 브랜드가 "KT"/"SKT"/
> "LG U+" 자체로 나오는데(진짜 알뜰폰 브랜드가 아님), 이 경우 `carrier_type`을
> `MNO`로 바로잡습니다(`crawl_moyo.py`의 `HOST_BRAND_MAP` 매칭). 안 그러면
> "너겟은 알뜰폰"처럼 잘못 분류됩니다.
| `host_mno` | 범주 | 실제 망 제공사: `KT` / `SKT` / `LGU+` | 없음 |
| `mvno_brand` | 문자열 | 알뜰폰 브랜드명 (예: `핀다이렉트`) | MNO 요금제 |
| `plan_id` | 문자열 | **기본키.** 혜택 테이블과 조인하는 키. 전체에서 유일함이 보장됨 | 없음 |

> LG U+는 `청년플러스150GB(키즈/청소년)`처럼 **한 요금제를 키즈 탭과 청소년 탭에
> 동시에** 올립니다. 그대로 두면 같은 `plan_id`가 두 행이 되어 혜택 조인이
> 뻥튀기되므로 `merge_plans.dedupe_plan_ids()`가 한 행으로 합칩니다(2026-08-20
> 기준 8건). 두 행은 `age_condition`만 다른데(만 12세 이하 / 만 18세 이하) 실제
> 가입 상한은 넓은 쪽이라 **큰 값을 남깁니다** — 좁은 쪽을 남기면 만 15세
> 사용자에게 이 요금제를 영영 추천할 수 없습니다. `plan_category`는 두 탭 이름을
> ` | `로 잇습니다.
| `base_plan_id` | 문자열 | 택1 전개 전의 원본 요금제 id. 전개되지 않은 행은 `plan_id`와 같음 | 없음 (항상 채워짐) |
| `plan_id_type` | 범주 | `official_code`(사이트 공식 코드) / `name_based`(코드가 없어 이름으로 생성) | 없음 |
| `plan_name` | 문자열 | 요금제명. 택1 전개 행은 `원래이름 (선택지)` 형식 | 없음 |
| `selected_option` | 문자열 | 이 행이 택1에서 고른 선택지 (예: `넷플릭스`) | **택1이 없는 요금제** |
| `plan_category` | 문자열 | 사이트 내 분류. KT는 탭명(`KT-통합요금제`/`KT-온라인전용(요고)`), SKT는 카테고리(`SKT-베스트`/`SKT-라이트`), LGU+는 탭명, 모요는 `moyo` 고정 | 없음 |
| `is_online_only` | 불리언 | 온라인 전용 가입 채널 (너겟/다이렉트/요고/모요) | 없음 |
| `age_condition` | 문자열 | 가입 자격·연령 조건 (예: `청년(Y덤)`, `만 65세 이상`, `키즈`) | **조건 없는 일반 요금제** |
| `signup_notice` | 문자열 | 가입 제한/유의사항 원문 (예: `이미 KT 요금제를 쓰고 있다면 이 요금제를 가입할 수 없어요`). 여러 개면 ` \| ` 로 연결 | **지금은 모요만 채움.** KT/SKT/LGU+ 자사 요금제는 이런 경고문이 사이트에 텍스트로 없음(제한이 없다는 뜻이 아니라 안 적혀 있다는 뜻) |

> **`signup_notice`는 모요 상세페이지의 "꼭 확인해 주세요" 배너**를 그대로 담습니다.
> 유형은 크게 6가지 — 모요 비제휴(도움 불가) · 신규가입 중단(번호이동만) · KB국민은행
> 계좌 필요 · 번호이동 90일 조건 · **동일 통신사 중복가입 불가**(너겟/요고/다이렉트처럼
> 통신 3사가 자사 온라인전용 상품을 모요로도 파는 경우, 이미 그 통신사를 쓰는
> 사람은 가입 불가) · 본인확인 서류 필요. 전체의 약 21.6%(585/2,703)에 있습니다.

> **`age_condition`은 두 가지를 함께 담습니다.** ① 일반 요금제의 **연령 보너스 변형**
> (KT 덤, SKT 청년 혜택 — `base_plan_id`가 원본을 가리킴)과 ② **연령 전용 상품**
> (`base_plan_id`가 자기 자신). 둘을 구분하려면 `base_plan_id == plan_id`로 보세요.
>
> **표기는 `만 N세 이하` / `만 N세 이상`으로 정규화되어 있습니다**
> (`schema.normalize_age_condition`). 원문은 사이트마다 제각각이라 그대로 두면
> 16종으로 갈라져서 나이로 거를 수가 없었습니다.
>
> | 원문 | 정규화 |
> |---|---|
> | `청년(Y덤)` (KT) · `청년(만 34세 이하)` (SKT) · `만 19세 ~ 35세 미만` (LGU+) | `만 34세 이하` |
> | `스쿨덤(청소년)` (KT) · `만 13세 ~ 19세 미만` (LGU+) | `만 18세 이하` |
> | `만 4세 ~ 13세 미만` (LGU+) | `만 12세 이하` |
> | `65세 이상` (KT) | `만 65세 이상` |
>
> 구간으로 적힌 것은 **상한만** 남깁니다(`만 4세 ~ 13세 미만` → `만 12세 이하`).
> 추천에서 실제로 걸리는 건 상한이기 때문입니다. LGU+의 하한(`만 4세 이상`)은
> 버려지지만 그 조건이 결과를 가르는 경우는 없습니다.
> 연령이 아닌 자격(`외국인`, `복지카드 소지 시`)은 원문 그대로 둡니다.
>
> KT는 이 조건을 본문이 아니라 **이미지 `alt`와 `<meta>`에만** 적어 둡니다
> (`<img alt="만 12세 이하 어린이용">`). 본문 텍스트만 훑으면 통째로 놓칩니다.

### 스펙

| 컬럼 | 타입 | 설명 | 빈값일 때 |
|---|---|---|---|
| `network_gen` | 범주 | `5G` / `LTE` | **세대 구분 없는 통합요금제** (KT 265행) |

> **빈값은 "모름"이 아니라 "5G/LTE 둘 다 가입 가능"입니다.** KT 상세페이지에는
> 세대 표기가 아예 없고(페이지에 있는 유일한 "5G"는 개발자가 남긴 주석 예시),
> 수집 대상 탭 이름부터가 "통합요금제"입니다. 예전에는 표기가 없으면 `5G`로
> 채웠는데 그러면 KT 284행이 전부 5G가 되고, LTE 사용자로 거를 때 통신3사
> 요금제가 10건까지 줄어듭니다. **필터링할 때 빈값은 어느 쪽으로도 걸러내지
> 마세요.** SKT(ledger 태그)와 LGU+(`plan-features`)는 사이트가 실제 값을
> 주므로 그대로 씁니다.
| `base_data_gb` | 실수 | 연령 조건과 무관한 **기본** 데이터 제공량 | 무제한 |
| `extra_data_gb` | 실수 | 연령 조건으로 **추가** 제공되는 데이터량 | 추가분 없음 |
| `data_gb` | 실수 | **월 총 제공량** = `base` + `extra` + `daily_data_gb`×30. **⚠ 아래 주의** | 무제한 |
| `data_unlimited` | 불리언 | 데이터 무제한 여부 | 없음 |
| `data_throttle_speed` | 문자열 | 소진 후 제어 속도 (예: `5Mbps`). **⚠ 아래 주의** | 속도 제어 없음/미표기 |

> **`data_throttle_speed`는 두 가지를 가리킵니다.** `data_unlimited=True`이면서
> 이 값이 있는 186행 중 **180행은 테더링 한도를 넘겼을 때의 속도**고(KT 초이스
> 더블: 테더링 90GB 후 100Kbps — 본 데이터는 진짜 무제한), **6행만 본 데이터
> 소진 후 속도**입니다(모요 `시월 무제한 7GB+1Mbps`). `tethering_gb`가 채워져
> 있으면 앞쪽, 비어 있으면 뒤쪽입니다(180 대 6, 겹침 0). 구분하지 않고 거르면
> 통신3사 프리미엄 요금제가 통째로 빠집니다. `docs/수정이력.md` 37번 참고.
| `daily_data_gb` | 실수 | 일 단위 제공량 (모요 일부 요금제) | 일 단위 제공 아님 |

> **`data_gb`는 일 단위 제공량을 월 환산해 더한 값입니다(사이트 표기와 다릅니다).**
> 사이트가 "월 11GB + 매일 2GB"처럼 단위를 섞어 적어서, 월 총량만 담으면 일
> 단위 제공분이 통째로 빠집니다(11GB로만 보임). 그래서 최종 CSV의 `data_gb`는
> **한 달에 실제로 쓸 수 있는 총량**으로 통일했습니다 — `merge_plans.build()`가
> `data_gb + daily_data_gb × 30`으로 채웁니다.
>
> | 사이트 표기 | `data_gb` | `daily_data_gb` |
> |---|---|---|
> | 월 11GB + 매일 2GB | `71.0` | `2.0` |
> | 매일 5GB (월 총량 표기 없음) | `150.0` | `5.0` |
> | 월 110GB | `110.0` | 빈값 |
>
> 해당 요금제는 295건(일 2GB 235 · 일 5GB 60)입니다. **사이트 원래 표기가
> 필요하면** `data_gb - daily_data_gb × 30`으로 되돌리거나 `data/interim/*.csv`
> (크롤러 출력, 합산 전)를 보세요. `agents/data_verify.py`가 상세페이지와
> 대조할 때 이 규칙을 씁니다.
>
> 두 가지 한계가 있습니다. ①한 달을 **30일 고정**으로 봅니다. ②일 단위 제공량은
> **이월되지 않으므로** 실사용 상한은 이 값보다 낮습니다(하루 5GB를 넘겨 쓰면
> 그날은 `data_throttle_speed`로 제한, 다음 날 다시 5GB). "월 150GB"짜리와
> 동일 취급하면 몰아 쓰는 사용자에게 잘못 추천됩니다.
>
> 이 295행은 `base_data_gb + extra_data_gb ≠ data_gb`입니다(위 예시: base 11,
> data_gb 71). `base`/`extra`는 **연령 조건별 추가 제공**을 나누는 칸이라 일
> 단위 합산분이 안 들어갑니다.
>
> 무제한은 여전히 **빈값**입니다(363행). 그 사실은 `data_unlimited`가 담고
> 있으므로 `9999` 같은 대체값을 넣지 않습니다 — 거리·유사도 기반 모델에서 그
> 한 축이 전체를 지배해 버립니다.
| `base_tethering_gb` | 실수 | 기본 **테더링+쉐어링 통합 한도** (아래 정의 참고) | 제공 없음/사이트 미표기 |
| `extra_tethering_gb` | 실수 | 연령 조건으로 추가되는 테더링량 | 추가분 없음 |
| `tethering_gb` | 실수 | **총 테더링+쉐어링 한도** = `base` + `extra` | 아래 `tethering_support`로 이유를 구분 |
| `tethering_support` | 범주 | `tethering_gb`가 빈 **이유**. `quota`(별도 한도 있음—값 채워짐) / `within_data`(별도 한도 없이 기본 데이터에서 차감, 테더링 자체는 됨) / `unsupported`(테더링 못 씀) / `undisclosed`(사이트 미공시) | 없음 |

> **`tethering_gb`가 비었다고 "테더링 없음"이 아닙니다.** 빈 이유가 세 가지인데
> 의미가 정반대라 `tethering_support`로 갈라 놨습니다. 전수 확인(2026-08-06,
> 모요 상세 2,305건): `unsupported` 1,023건(44.4%) · `undisclosed` 450건(19.5%) ·
> `within_data` 378건(16.4%) · `quota` 454건(19.7%). 빈칸 중 55%가 실제로는
> 테더링이 안 되는 요금제라, 전부 "미공시"로 보면 크게 틀립니다.
>
> 지원 여부는 렌더된 "지원/미지원" 섹션이 아니라 **`<meta name="description">`**
> 에서 읽습니다. 그 섹션이 통째로 안 실린 캐시 페이지가 많아서(불완전 캐시),
> 섹션만 보면 미지원 요금제를 미공시로 오인합니다(섹션 기준 79건 → 메타 기준
> 1,023건). **모요만 네 값을 다 구분**하고, KT/SKT/LGU+는 그런 섹션이 없어서
> 값이 있으면 `quota`, 없으면 `undisclosed`까지만 채웁니다.
| `voice_unlimited` | 불리언 | 음성통화 무제한 여부 | 없음 |
| `voice_minutes` | 정수 | 음성 제공 분수 | 무제한 |
| `voice_extra_minutes` | 정수 | 영상/부가통화 제공 분수 | 제공 없음 |
| `sms_unlimited` | 불리언 | 문자 무제한 여부 | 없음 |
| `sms_count` | 정수 | 문자 제공 건수 | 무제한 |

> ### `tethering_gb`의 정확한 의미
>
> 이름은 "테더링"이지만 실제로 담는 값은 **테더링 + 데이터 쉐어링 통합 한도**입니다.
> 사이트마다 부르는 이름이 달라서 헷갈리기 쉬운데, 원문 표현은 이렇게 대응됩니다.
>
> | 사이트 | 원문 표현 | 이 컬럼에 들어가나 |
> |---|---|---|
> | KT | `공유데이터 100GB` | ✅ |
> | SKT | `shrDataQtyCtt` | ✅ |
> | LG U+ | `테더링+쉐어링 100GB` | ✅ |
> | LG U+ | `테더링+쉐어링 기본 제공량 내 60GB` | ✅ (기본 제공량 **안에서의 한도**) |
> | LG U+ | `참 쉬운 가족 데이터 50GB` | ❌ **가족 간 공유는 다른 개념** |
> | KT | `데이터 쉐어링 1회선 할인` | ❌ 용량이 아니라 **회선 요금 할인** (→ `스마트기기` 혜택) |
>
> **가족 데이터 공유는 의도적으로 제외**했습니다. 내 회선에서 쓸 수 있는 양이 아니라
> 가족과 나눠 쓰는 별도 부가서비스라, 같은 컬럼에 넣으면 의미가 섞입니다.
> 필요하면 혜택 테이블에서 `참 쉬운 가족 데이터`로 조회하세요.
> (플러스플랜115처럼 `테더링+쉐어링 100GB`와 `가족 데이터 50GB`를 **둘 다** 가진
> 요금제가 실제로 있습니다. 이 경우 컬럼에는 100만 들어갑니다.)
>
> **MVNO(모요)는 658 / 2,173만 채워집니다.** 목록 카드에는 테더링 정보가 아예 없고,
> 상세페이지 "지원" 섹션의 `모바일 핫스팟` 항목에서만 얻을 수 있습니다. 그 항목이
> `통신사 문의`(값 미공개)거나 `데이터 제공량 내 이용 가능`(별도 할당 없음)인 경우가
> 많아 빈칸이 남습니다.

> **`base` / `extra` / `총량` 3단 구조**는 연령별 추가 제공 때문입니다.
> 예) KT `베이직100`의 Y덤 행 → `base_tethering_gb=70`, `extra_tethering_gb=70`, `tethering_gb=140`.
> SKT도 같은 구조를 씁니다(아래 연령 혜택 참고). LGU+/모요는 `base == 총량`으로 자동 채워집니다.

#### 연령 혜택 행 (KT 덤 / SKT 연령 혜택)

연령에 따라 **제공량이나 스펙이 실제로 달라지는** 요금제는 조건별로 행을 나눕니다.
같은 요금제의 다른 연령 행은 `base_plan_id`로 묶입니다.

| `age_condition` | 사이트 | 행 수 |
|---|---|---|
| `청년(Y덤)` / `스쿨덤(청소년)` / `65세 이상` / `75세 이상` | KT | 덤 표 기준 |
| `청년(만 34세 이하)` | SKT | 38 |
| `청소년(만 18세 이하)` | SKT | 3 |
| `청년(만 19세~34세)` | SKT | 3 |
| `시니어(만 65세 이상)` | SKT | 5 |

- SKT는 대부분 **우산 라벨 `만 34세 이하` 하나**만 씁니다. 상세페이지가 청소년/청년을
  따로 적은 3개 요금제(`T플랜 세이브`, `라이트 39`, `라이트 45`)만 값이 달라서 나눕니다.
  나머지는 두 구간의 값이 같아(셀 병합) 우산 라벨로 충분합니다.
- **할인만 있고 제공량이 그대로인 요금제는 행을 늘리지 않습니다**(예: 커피/영화/로밍 50%
  할인만 받는 SKT 요금제 43개). 스펙이 동일한 행이 두 줄 생기는 것을 막고, 혜택 행으로만
  기록합니다.
- `age_condition`에는 연령이 아닌 가입 자격(`복지` 등)도 들어옵니다. **연령 상품 여부를
  판별할 때는 `만 N세` 패턴으로 확인해야 합니다** (`복지` 요금제인 `소리누리`에도
  시니어 혜택이 따로 있습니다).

> ### 초과 사용 요금 컬럼은 제거되었습니다
>
> `overage_data_won_per_mb` / `overage_voice_won_per_sec` / `overage_sms_won_per_msg` /
> `overage_video_call_won_per_sec` / `video_call_deduction_rate` 5개 컬럼은 스키마에서
> 뺐습니다. 데이터 소진 후 동작은 `data_throttle_speed`로 확인하세요.

### 가격

| 컬럼 | 타입 | 설명 | 빈값일 때 |
|---|---|---|---|
| `monthly_fee` | 정수 | **정가** 월정액(원) | 없음 |
| `discounted_fee` | 정수 | **실제 내는 돈**(원). 할인이 없으면 `monthly_fee`와 같은 값 | 정가도 없는 경우만 |
| `discount_type` | 문자열 | 할인 종류 (예: `선택약정 25% 할인`) | 할인 없음 |
| `discount_period_months` | 정수 | 할인 적용 개월 수 (모요 프로모션) | 기간 제한 없음 |

> **⚠️ MVNO(모요)는 의미가 다릅니다.** 모요는 "N개월 이후 정상가"가 표기되므로
> `monthly_fee`=프로모션 종료 후 정상가, `discounted_fee`=현재 실제 납부액입니다.
> MNO는 `monthly_fee`=정가, `discounted_fee`=선택약정 할인가입니다.
> **두 통신사 유형을 함께 비교할 때는 `discounted_fee`(실제 내는 돈) 기준으로 봐야 합니다.**
>
> **할인이 없어도 `discounted_fee`는 비지 않습니다.** 온라인 전용(KT 요고 13 ·
> LGU+ 너겟 46 · SKT 다이렉트 31)은 선택약정 대상이 아니라 예전에는 이 값이
> 비어 있었는데, 가격 결측을 거르는 쪽에서 **3사 최저가 라인 90개가 통째로
> 사라졌습니다.** 지금은 정가로 채웁니다. 할인 여부는 `discount_type`(빈값)이나
> `monthly_fee == discounted_fee`로 구분하세요. `docs/수정이력.md` 38번 참고.

### 혜택 요약

상세 내역은 혜택 테이블에 있고, 여기는 조회 편의를 위한 요약입니다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `benefit_count` | 정수 | 이 요금제에 달린 혜택 행 개수 |
| `ott_option_count` | 정수 | OTT/구독 혜택 개수 |
| `ott_options` | 문자열 | OTT 서비스명 목록 (` \| ` 구분) |
| `membership_grade` | 문자열 | **정규화된** 멤버십 등급: `VVIP` / `VIP` (아래 참고) |
| `smart_device_benefit` | 문자열 | 스마트기기 회선 혜택 |
| `extra_data_benefit` | 문자열 | 추가/공유 데이터 혜택 |
| `gift_benefit` | 문자열 | 사은품/페이백 |

> ### `membership_grade`는 정규화된 값입니다
>
> 통신사별 원문 표기가 제각각이어서 등급만 뽑아 통일했습니다.
>
> | 원문 | 이 컬럼 |
> |---|---|
> | `멤버십 VVIP` (KT) / `VVIP 등급` (LGU+) | `VVIP` |
> | `멤버십 VIP` (KT) / `T 멤버십 VIP 혜택` (SKT) / `24개월간 VIP 등급` (LGU+) | `VIP` |
>
> 덕분에 `membership_grade == "VVIP"` 같은 필터가 3사 공통으로 동작합니다.
> `24개월간` 같은 부수 조건이 필요하면 혜택 테이블의 `benefit_name`을 보세요.

> **⚠️ 택1이 남아있는 경우 주의.** 택1 그룹이 2개 이상이면 **가장 큰 그룹 하나만** 펼칩니다.
> 예) KT 초이스130은 `초이스(9개)`를 펼치고 `플러스(3개)`는 그대로 둡니다. 따라서
> `초이스130 (넷플릭스)` 행의 `ott_options`는 `넷플릭스 | 지니뮤직 | 밀리의서재`가 되는데,
> 이 중 **넷플릭스만 확정이고 나머지 2개는 아직 택1 상태**입니다.
> 정확히 구분하려면 혜택 테이블의 `is_selectable` 컬럼을 보세요.

| `new_subscribers` | 정수 | **하루당** 신규 가입 = 직전 스냅샷 대비 증가분 ÷ 스냅샷 간격(일) | 위와 같음 |
| `subscriber_count_source` | `crawled` / `estimated` | `subscriber_count`가 실측인지 난수인지 | 없음 |
| `new_subscribers_source` | `crawled` / `estimated` | `new_subscribers`가 실측 차분인지 난수인지 | 없음 |

> "10+명이 선택"처럼 정확한 수 대신 하한으로 표시되는 경우가 있습니다(인기가
> 낮은 요금제). 이때도 `10`을 그대로 저장하므로 **실제보다 낮게 잡힐 수
> 있습니다.**

#### 일별 신규 가입자와 난수 채우기

`subscriber_count`는 누적값이라 일별 신규 가입은 스냅샷 차분으로 냅니다. 갱신을
거른 날이 있으면(예: 08-15~17) 인접한 두 스냅샷이 하루 간격이 아니므로, 차분을
그 간격(`days_elapsed`)으로 나눠 **하루당 증가 수**로 맞춥니다.
`src/subscriber_trend.py`가 `data/final/history/*/`의 일자별 백업을 읽어
`(date, plan_id, subscriber_count, new_subscribers)` 시계열을 만들고,
`src/fill_subscriber_daily.py`가 그 결과를 최종 CSV에 붙입니다.

값을 알 수 없는 칸은 **현재 분포에서 뽑은 난수**로 채우고 `estimated`로
표시합니다. 가중치·통계로 쓸 때는 이 컬럼으로 실측만 걸러낼 수 있습니다.

> **출처 컬럼이 두 개인 이유**: 누적은 실측인데 하루 증가만 모르는 행이 많습니다
> (카운터 리셋 773행). 한 컬럼으로 뭉치면 그 행 전체가 난수 취급을 받아, 실제로
> 크롤링해 온 누적값이 다음 날 차분 계산에서 통째로 빠집니다.

| 대상 | 개수(2026-08-19 기준) | 채우는 방법 |
|---|---|---|
| MNO 요금제 | 548 | 모요 MVNO 2,211개의 `subscriber_count` 경험분포에서 부트스트랩. 요금·데이터량과 인기의 상관이 사실상 0(로그 상관 -0.02 / 0.13)이라 구간을 나눠 뽑지 않습니다 |
| 직전 스냅샷이 없는 신규 요금제 | 9 | 관측된 하루당 증가율(하루당 신규 ÷ 누적) 분포에서 뽑아 그 행의 `subscriber_count`에 곱함 |
| 차분이 음수인 행 | 521 | 위와 같음. 모요가 요금제 개편 시 카운터를 0부터 다시 세기 때문에(하루 -5만도 나옵니다) 실제 신규 가입을 알 수 없습니다 |

`refresh_plans.py`가 최종 CSV를 새로 쓰면 두 컬럼은 사라집니다. 갱신 뒤
`python src/fill_subscriber_daily.py`를 다시 돌리세요(시드 고정이라 같은 값이
나옵니다).

#### 일별 패널 (`통신요금제_가입자일별_최종.csv`)

요금제 × 날짜 격자입니다. 통합데이터가 "오늘 하루"만 담는 것과 달리, 날짜마다
누적/신규를 한 행씩 담습니다. `plan_id`로 통합데이터와 조인합니다.

**알뜰폰(MVNO) 2,210개만 들어갑니다.** 3사(MNO)는 사이트에 "N명이 선택" 같은
표시가 없어 되감을 기준점이 난수뿐이고, 그 난수는 모요 MVNO 분포에서 뽑은 것이라
실제 3사 가입자(요금제당 수십만~수백만)와 자릿수가 다릅니다. 30일치를 채워 두면
"MNO 대 MVNO 추이" 같은 성립하지 않는 비교를 부르므로 뺐습니다.

```
python src/build_subscriber_panel.py            # 최근 30일
python src/build_subscriber_panel.py --days 60
python src/build_subscriber_panel.py --wide     # 요금제 1행 × 날짜 컬럼(엑셀용)
```

| 컬럼 | 설명 |
|---|---|
| `plan_id` / `plan_name` / `carrier_type` | 통합데이터와 동일 |
| `date` | `YYYY-MM-DD` |
| `subscriber_count` | 그 날의 누적 가입자 |
| `new_subscribers` | 그 날 하루 증가분 (첫날은 0, 카운터 리셋으로 생기는 음수는 0) |
| `subscriber_count_source` | `crawled`(그 날 스냅샷이 실제로 있음) / `estimated` |

**칸의 87%는 추정값입니다**(30일 × 2,759행 중 실측 10,448칸). 실측 스냅샷이
5일치(08-11/13/14/18/19)뿐이라 나머지는 이렇게 만듭니다.

| 구간 | 방법 |
|---|---|
| 스냅샷 사이 | 양 끝 실측을 선형 보간 (08-14 → 08-18의 4일치를 하루씩 나눔) |
| 첫 실측 이전 | 그 요금제의 관측된 하루당 증가율 `r`로 되감기: `count(d-1) = count(d) / (1+r)`. 1명 밑으로 내려가면 0(미출시)으로 둠 |
| 구간 중간에 100명 이하로 처음 등장 | 등장 전날까지 0. 실제로 그때 출시된 것으로 봄 |

되감기 증가율은 **0.05/일로 자릅니다**(관측된 요금제별 중앙값의 95분위).
안 자르면 최대 0.199가 그대로 30일 복리로 걸려 "한 달 만에 237배"라는 과거가
만들어집니다. 처음부터 수만 명인 채로 목록에 등장한 요금제(모요 목록에 늦게
올라온 것)를 "그날 출시"로 보면 하루 신규가 27,000명씩 튀어서, 100명 이하만
신규 출시로 봅니다.

> 한계: 되감기는 "지금 증가율이 과거에도 같았다"고 가정합니다. 실제로는 출시
> 직후가 가장 빠르고 뒤로 갈수록 완만하므로 **과거 값은 실제보다 높게** 잡힙니다.
> 스냅샷이 하루씩 쌓이면 그만큼 보간(실측 사이)으로 대체됩니다.
>
> 매일 값이 바뀌는 지표라 요금제 갱신 판단(`refresh_plans.py`의 변경 감지)에는
> **쓰이지 않습니다.** 여기 값이 바뀐 것만으로는 상세 페이지를 다시 받지
> 않습니다 - 안 그러면 스펙이 그대로여도 사실상 전체 요금제가 매일 "변경됨"으로
> 잡혀 모요 상세 2,200여 건을 매번 다시 받게 됩니다.

## 택1(선택형) 혜택 처리 방식

### 왜 펼치는가

SKT는 **처음부터 선택지마다 별도 상품**으로 만들어 놓았습니다.

```
베스트 Max(넷플릭스)     129,000원   prodId = NA00009815
베스트 Max(디즈니+)      129,000원   prodId = NA00009816
```

반면 KT 초이스와 LGU+ 프리미엄플러스는 한 요금제 안에 선택지가 목록으로만 들어 있습니다.
그대로 두면 *"SKT는 요금제마다 OTT 1개, KT는 요금제마다 OTT 9개"* 처럼 보여서,
순전히 파싱 방식 때문에 생긴 왜곡이 그대로 모델에 들어갑니다.
그래서 **KT/LGU+도 SKT와 같은 입도로 맞춰** 펼칩니다.

### 규칙

1. 택1 그룹이 여러 개면 **선택지가 가장 많은 그룹 하나만** 펼칩니다.
   (KT: 초이스 9개 vs 플러스 3개 → 초이스만. 전 조합 9×3=27로 펼치면 행이 급증하는 데 비해
   SKT가 실제로 쓰는 입도는 "주 OTT 하나"이므로 거기에 맞춥니다.)
2. 펼친 행의 혜택 목록에는 **고른 선택지 1개 + 택1이 아닌 나머지 혜택**만 남습니다.
   → 나중에 혜택 금액을 합산할 때 그냥 `sum`하면 되고, "택1은 max로 묶어야 한다" 같은
   예외 규칙이 필요 없습니다.
3. `base_plan_id`로 원본 요금제를 되짚을 수 있습니다.

### 알려진 예외 / 한계

| 항목 | 내용 |
|---|---|
| KT `플러스` 그룹 | 펼치지 않으므로 `ott_options`에 미확정 선택지가 섞여 있습니다 (위 ⚠️ 참고) |
| KT `티빙/지니/밀리` | 원문상 **하나의 선택지**입니다 (KT도 "초이스 티빙/지니/밀리"라는 단일 상품으로 부름). 3개로 분리하지 않습니다 |
| KT `초이스 더블` | 택1이 **아닙니다.** 디즈니+와 단말보험 할인을 **둘 다** 제공하므로 펼치지 않습니다 |
| KT 플러스 미제공 조건 | 원문에 *"티빙/지니/밀리 초이스는 플러스 혜택 미제공"* 이라는 조건이 있으나, 현재 데이터에는 반영되어 있지 않습니다 |
| 연령대 × 택1 | KT 초이스130/110/90은 연령대 5종 × 선택지 9종으로 곱해집니다 |
| LG U+ `데일리플러스` 그룹 | 6개 요금제에 `프리미엄플러스`와 별개인 두 번째 택1 그룹이 있습니다(구글원 / 모아진 / 교보문고 sam / 지니뮤직 / 밀리의 서재). 선택지가 5개로 프리미엄플러스보다 적어 규칙 1에 따라 펼치지 않고, 혜택 행으로만 남습니다 |
| LG U+ 너겟75 | `프리미엄플러스(택1)` 선택지가 원문에도 `삼성디바이스` **하나뿐**입니다(요금제별 안내표로 확인). 선택지가 1개면 고를 것이 없어 펼치지 않습니다 — 누락이 아닙니다 |

## `plan_id` 생성 규칙

| 사이트 | 형식 | 예 |
|---|---|---|
| KT | `{ItemCode}_{요금제명}` | `1681_초이스130` |
| SKT | 사이트 상품코드 그대로 | `NA00009815` |

여기에 아래 접미사가 **필요한 경우에만** 붙습니다.

| 접미사 | 의미 | 예 |
|---|---|---|

> `#N`은 표 안에 이름·가격이 완전히 같고 옵션만 다른 행이 여러 번 나올 때만 붙습니다
> (KT `데이터투게더` 등). 중복이 아닌 요금제의 id는 건드리지 않으므로,
> 기존 id로 조인하던 코드가 깨지지 않습니다.

### 요금제명 추출 순서 (KT)

KT는 표마다 요금제명 컬럼 헤더가 달라서 아래 순서로 찾습니다.

1. `요금제` / `구분` / `요금제명` / `상세요금제` / `상품명` 중 정확히 일치하는 컬럼
2. 헤더에 `요금제`(단, `월정액` 제외) 또는 `상품명`이 포함된 컬럼
3. **페이지 `<title>`** — 구형 3G/피처폰 페이지는 요금제가 1개뿐이라 표에 이름 컬럼이
   아예 없습니다 (`신 표준`, `슬림`, `손말 요금제` 등이 여기서 나옵니다)

---

## 수집 파이프라인

```
src/crawl_kt.py  crawl_skt.py  crawl_lguplus.py  crawl_moyo.py
        │  fetch_all()  : 원본 HTML·JSON을 data/raw_cache/<사이트>/ 에 저장
        │  parse_all()  : 캐시만 읽어서 파싱 (네트워크 요청 없음)
        ▼
data/interim/{kt,skt,lguplus,moyo}_{plans,benefits}.csv
        ▼  src/merge_plans.py
data/final/통신요금제_통합데이터_최종.csv
           통신요금제_혜택상세_최종.csv
```

원본을 캐시에 남기므로, 파싱 로직을 고쳤을 때 **재크롤링 없이** 다시 파싱할 수 있습니다.

```bash
python src/crawl_kt.py --parse-only
```

### 경로 규칙

모든 경로는 `schema.py`의 상수를 씁니다. `schema.py` 파일 위치를 기준으로 잡으므로
**어느 디렉터리에서 실행해도** 같은 곳을 읽고 씁니다.

| 상수 | 가리키는 곳 | 용도 |
|---|---|---|
| `BASE_DIR` | `src/`의 부모 = 프로젝트 루트 | 기준점 |
| `RAW_CACHE_DIR` | `data/raw_cache` | 사이트 원본 HTML·JSON |
| `INTERIM_DIR` | `data/interim` | 사이트별 중간 CSV |
| `FINAL_DIR` | `data/final` | 합친 최종 CSV |

```python
cache_dir("kt")                # -> data/raw_cache/kt
interim_path("kt_plans.csv")   # -> data/interim/kt_plans.csv
final_path("…_최종.csv")        # -> data/final/…_최종.csv
```

> 폴더 구조를 또 바꾸려면 **위 상수만 수정**하면 되고, 크롤러 4개는 손대지 않아도
> 됩니다. `write_plans`/`write_benefits`와 `merge_plans.py`는 저장 직전에 상위
> 폴더를 자동으로 만들기 때문에 폴더를 미리 만들어 둘 필요도 없습니다.

전체 재수집이 필요하면 `--parse-only`를 빼고 실행합니다.
`merge_plans.py`는 각 사이트 CSV의 컬럼이 `schema.py`와 일치하는지 `assert`로 검사하므로,
스키마를 바꾸면 4개 크롤러를 모두 다시 돌려야 합니다.
