2. 왜 Workflow를 두 개로 분리했는가?

여기서 멘토님한테 설계 이유를 설명해.

“요금제 데이터가 수시로 변경될 수 있기 때문에 데이터 갱신 기능도 필요하다고 판단했습니다. 다만 사용자가 추천을 요청할 때마다 크롤링하면 응답 시간이 길어지고 크롤링 실패가 추천 서비스까지 영향을 줄 수 있기 때문에, 추천 Workflow와 데이터 갱신 Workflow를 분리했습니다.”

따라서:

Recommendation Workflow

사용자가 요청할 때 실행.

사용자 요청
   ↓
요구사항 분석
   ↓
DB에서 후보 검색
   ↓
추천
   ↓
검증
   ↓
응답
Plan Update Workflow

사용자 요청과 상관없이 주기적으로 실행.

Scheduler
   ↓
크롤링
   ↓
정규화
   ↓
DB 갱신

그리고 둘의 연결점은 Plan DB 하나라고 설명하면 돼.

Plan Update
    ↓
  Plan DB
    ↑
Plan Search

이건 꽤 중요한 설계 포인트야.

3. 그럼 Orchestrator가 정확히 뭘 하느냐

여기서는 5개만 말하면 돼.

“Orchestrator는 직접 추천 알고리즘을 수행하는 Agent라기보다 각 전문 Agent가 협업할 수 있도록 전체 실행 흐름을 관리합니다.”

구체적으로:

① State 관리
② Agent 실행 순서 관리
③ 조건에 따른 Routing
④ 실패 시 Retry / Re-routing
⑤ Agent 간 Input / Output Interface 관리

이게 네 역할이야.

4. State를 왜 만들었는가

예시를 하나 들어.

사용자가:

KT망 알뜰폰 중 월 3만원 이하, 데이터 20GB 이상 추천해줘.

라고 하면 처음에는:

user_query

만 있어.

User Analysis가 실행되면:

user_profile = {
    "budget_krw": 30000,
    "monthly_data_gb": 20,
    "preferred_carrier": "KT",
    "carrier_type": "MVNO"
}

가 State에 추가돼.

그다음:

Plan Search
      ↓
candidate_plans 저장


Recommendation
      ↓
recommendations 저장


Validation
      ↓
validation_result 저장


Response
      ↓
final_response 저장

즉 State가 점점 이렇게 채워지는 거야.

TelecomState


user_query
    ↓
user_profile
    ↓
candidate_plans
    ↓
recommendations
    ↓
validation_result
    ↓
final_response

그래서 이렇게 설명하면 돼.

“Agent끼리 서로 직접 의존해서 데이터를 전달하지 않고, LangGraph의 공유 State를 통해 결과를 전달하도록 구성했습니다.”

6. 왜 Interface가 필요한가?

여기서 팀 분업 이야기를 연결하면 돼.

“현재 Agent별 담당자가 다르기 때문에 각자 코드를 자유롭게 개발하면 함수명이나 반환 데이터 구조가 달라질 수 있습니다. 그러면 통합 단계에서 Orchestrator를 계속 수정해야 합니다.”

예를 들어 인터페이스가 없으면:

User Analysis 팀
→ {"budget": 30000}


추천 팀
→ budget_krw를 기대


Validation 팀
→ monthly_fee를 기대


Orchestrator
→ 전부 변환해야 함

문제가 생겨.

그래서 처음부터:

class UserProfile(BaseModel):
    budget_krw: int | None
    monthly_data_gb: float | None
    ...

처럼 공통 규격을 만드는 거야.

그럼:

User Analysis
      │
      │ UserProfile
      ▼
Recommendation
      │
      │ RecommendationItem[]
      ▼
Validation

으로 연결돼.

7. 그리고 내부 구현은 자유롭다

이것도 꼭 이야기해.

예를 들어 추천 담당자가 내부적으로:

Rule-based
가중치 Scoring
ML
LLM
Hybrid Recommendation

중 뭘 사용하든 Orchestrator는 신경 쓰지 않아.

단지:

recommend(
    profile,
    candidates
) -> list[RecommendationItem]

이라는 계약만 지키면 돼.

그래서:

“Agent 내부 구현과 Orchestration Layer를 분리해서, 나중에 Agent 구현 방법이 변경돼도 전체 Workflow를 수정하지 않는 구조를 목표로 했습니다.”

이 표현이 좋아.

8. 팀원 코드가 완성되면 어떻게 붙이는가?

이것도 실제로 보여줘.

현재는:

Orchestrator
     │
     ├── Mock User Analysis
     ├── Mock Recommendation
     ├── Mock Validation
     ├── Mock Response
     └── Mock Plan Update

이야.

팀원 코드가 완성되면:

Orchestrator
     │
     ├── 실제 User Analysis Agent
     ├── 실제 Recommendation Agent
     ├── 실제 Validation Agent
     ├── 실제 Response Agent
     └── 실제 Plan Update Agent

로 교체.

코드상으로는 bootstrap.py에서:

user_analyzer=RuleBasedUserAnalyzer()
recommender=WeightedRuleRecommender()
validator=ConstraintValidator()
plan_updater=ReloadOnlyPlanUpdater()

같은 Mock 구현을:

user_analyzer=TeamUserAnalysisAgent()
recommender=TeamRecommendationAgent()
validator=TeamValidationAgent()
plan_updater=TeamPlanUpdateAgent()

로 바꾸는 거야.

그리고:

“팀원이 Agent를 완성하면 Workflow를 다시 작성하는 게 아니라 Interface를 만족하는지 확인한 후 Dependency만 실제 구현체로 교체해서 통합합니다.”

라고 설명하면 돼.

9. 지금 추천 결과가 나오는 건 뭐냐?

이건 멘토님한테 숨기면 안 되고 오히려 명확하게 말하는 게 좋아.

현재:

KT망 알뜰폰 중
3만원 이하
20GB 이상 추천해줘

라고 하면 실제로 결과가 나오잖아.

그런데 이건 최종 추천 Agent가 완성된 게 아니야.

설명은:

“현재 다른 Agent들이 완성되기 전에도 Orchestrator 전체 흐름을 테스트할 수 있도록 Mock Agent를 만들어 연결했습니다.”

현재 User Analysis는 임시 Rule/Regex 기반.

"3만원 이하"
→ budget_krw = 30000


"20GB 이상"
→ monthly_data_gb = 20


"KT망"
→ preferred_carrier = KT

후보 검색은 현재 크롤링해놓은 실제 요금제 CSV를 사용.

그리고 Recommendation은 임시로:

가격
데이터
QoS
혜택
통화
문자

등에 가중치를 주는 baseline scoring.

그래서 TOP 3가 나오는 거야.

즉:

“현재 출력되는 추천 결과는 추천 성능을 보여주기 위한 것이 아니라 Orchestrator의 End-to-End Workflow가 정상적으로 연결되는지를 확인하기 위한 Mock 결과입니다.”

이렇게 말하면 정확해.

10. Plan Update도 현재는 똑같아

현재 Plan Update Agent 역시 실제 크롤러가 완성된 게 아니야.

현재는:

Plan Update Workflow
        ↓
Mock PlanUpdater
        ↓
기존 Repository reload
        ↓
PlanUpdateResult 반환

을 통해 갱신 Workflow 자체가 정상적으로 연결되는지만 확인하는 단계야.

나중에 데이터 담당자가:

SKT crawler
KT crawler
LGU+ crawler
MVNO crawler
Normalization
DB Upsert

를 구현하면 Mock PlanUpdater를 실제 구현으로 교체.

이렇게 해두면 “지금 어디까지 했는가?” 질문에도 바로 답할 수 있어.

멘토님 앞에서는 최종적으로 이렇게 말하면 돼

“전체적으로는 사용자 추천 요청을 처리하는 Recommendation Workflow와 요금제 데이터를 관리하는 Plan Update Workflow를 분리했습니다. Orchestrator에서는 각 Agent의 실행 순서, 공유 State, 조건부 Routing과 Retry를 관리하고 있습니다.”

“또한 팀원별로 Agent 담당이 다르기 때문에 Agent 내부 구현과 Orchestrator가 강하게 결합되지 않도록 Pydantic Schema와 Interface를 통해 Input/Output 계약을 정의했습니다.”

“현재는 실제 Agent가 아직 완성되지 않은 부분에 동일한 Interface를 만족하는 Mock Agent를 연결해 End-to-End Workflow를 테스트하고 있습니다. 이후 각 담당자의 Agent가 완성되면 Mock을 실제 구현체로 교체해서 통합할 예정입니다.”

“요금제 갱신 역시 사용자 요청마다 크롤링하는 방식이 아니라 별도의 Plan Update Workflow에서 주기적으로 데이터를 수집·정규화하고 DB를 갱신하고, Recommendation Workflow는 갱신된 DB를 조회하는 구조로 설계했습니다.”
